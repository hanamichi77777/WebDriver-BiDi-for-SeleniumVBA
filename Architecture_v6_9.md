## Chapter 1 — Native WinSock WebSocket Transport and RFC 6455 Control

The transport replaces the legacy WinHTTP WebSocket implementation with a native WinSock one. The design goal is not merely to change the API used for WebSocket I/O, but to remove the last architectural source of Office host freezes: a synchronous receive call that could fail to return when the peer stayed TCP-alive but stopped delivering WebSocket frames. The communicator now owns the TCP socket, the RFC 6455 handshake, WebSocket framing, masking, ping/pong handling, the UTF-8 text codec, request IDs, the dual-bounded event FIFO, application-heartbeat state, and monotonic timing as one transport layer.

## WinSock API Ownership

The transport calls `ws2_32.dll` directly through `WSAStartup`, `WSACleanup`, `socket`, `ioctlsocket`, `connect`, `select`, `getsockopt`, `setsockopt`, `send`, `recv`, `shutdown`, `closesocket`, `WSAGetLastError`, and `InetPtonW`. The socket is put into non-blocking mode with `FIONBIO`, so the native layer never waits indefinitely inside a blocking receive. Connection progress is driven by bounded `select`/`getsockopt(SO_ERROR)` polling rather than a blocking `connect` call.

Only local, unencrypted `ws://` endpoints are accepted. `localhost`, `127.0.0.1`, and `[::1]` are the permitted host forms, and `AttemptAutoConnect` accepts only driver-issued WebSocket URLs containing `/session`. Symbolic `localhost` first tries IPv6 loopback and falls back to IPv4 only if the transport fails before the WebSocket opens; explicit numeric hosts preserve the caller’s address family.

## Seven-Stage WinSock / WebSocket Handshake Sequence

The `Connect` path now establishes the BiDi channel through this sequence:

1. `WSAStartup` — Initialize WinSock 2.2 once for the communicator.
2. `socket` — Create an IPv4 or IPv6 TCP socket.
3. `ioctlsocket(FIONBIO)` — Switch the socket to non-blocking mode.
4. `connect` + `select` + `getsockopt(SO_ERROR)` — Complete TCP connection within the bounded connect deadline.
5. HTTP/1.1 WebSocket upgrade request — Send `Host`, `Upgrade: websocket`, `Connection: Upgrade`, `Sec-WebSocket-Key`, `Sec-WebSocket-Version: 13`, and `User-Agent` headers. Deliberately do **not** send `Origin`: Firefox RemoteAgent rejects a non-empty `Origin` with HTTP 400, so Origin non-emission is a transport invariant.
6. Status/header validation — Confirm `101 Switching Protocols`, `Upgrade: websocket`, `Connection: upgrade`, and the expected `Sec-WebSocket-Accept` value.
7. Transport open — Enter `WsTransportOpen`, reset session counters, and expose the connection to the BiDi command layer.

The `Sec-WebSocket-Key` is generated from native randomness and the expected accept value is computed from the RFC 6455 GUID using SHA-1 and Base64. This keeps the handshake independent of WinHTTP while still validating the browser driver’s protocol switch strictly.

## RFC 6455 Frame Engine

After the handshake, the communicator parses and emits WebSocket frames itself. Client-to-server frames are masked, large payload lengths are encoded according to RFC 6455, and outbound frames are written through a send queue so partial `send` completions are resumed correctly. Inbound bytes are accumulated in a raw buffer, decoded by a state machine, and converted into complete text messages before the outer BiDi layer sees them.

The frame parser handles text, continuation, close, ping, and pong opcodes. Browser ping frames are answered with pong frames. The client also maintains its own lightweight WebSocket ping interval, separate from the BiDi `session.status` heartbeat managed by the communicator’s `GetMessage` polling path.

## UTF-8 Codec Ownership

The transport converts between VBA’s UTF-16 strings and RFC 6455 UTF-8 payloads itself, calling kernel32’s `WideCharToMultiByte` and `MultiByteToWideChar` rather than delegating the conversion to a COM stream object.

The reason is invariant ownership rather than speed. RFC 6455 assigns the rule “a text frame payload must be valid UTF-8” to the WebSocket layer, and requires an endpoint that receives malformed UTF-8 to fail the connection. A converter that silently substitutes U+FFFD for malformed input cannot detect the very violation the layer is responsible for detecting. The corruption then reappears two layers higher as a JSON parse error, in a component that neither owns the invariant nor can diagnose it. Strict conversion flags — `MB_ERR_INVALID_CHARS` on decode and `WC_ERR_INVALID_CHARS` on encode — move detection back to the layer that owns it.

Abstraction fit is the second reason. A stream object exists to hold data in flight; this code path needs a pure function. The previous implementation opened a stream, wrote text, rewound, switched type, skipped the three BOM bytes the stream itself had inserted, read the result, and discarded the object. Stripping an artifact that the abstraction added is a reliable sign that the abstraction is the wrong one. The same transport already owns Base64, host-to-network port conversion, and ASCII encoding in its own code, and computes SHA-1 by calling Windows CNG (`BCrypt*` in `bcrypt.dll`) directly rather than through a COM object, so the text codec now follows the same ownership model.

**Receive side.** Decoding occurs only after the complete WebSocket text message is available. For the common non-fragmented case, the parser decodes directly from the contiguous raw receive buffer after the full payload is present. Fragmented text is accumulated only while the message remains within the configured limit and is decoded after the final continuation frame. A multi-byte UTF-8 sequence split across TCP reads, pump boundaries, or WebSocket continuation frames therefore never reaches the decoder half-formed.

**Malformed peer text.** A decode rejection raises `WS_ERR_INVALID_UTF8`, and the transport answers with an RFC 6455 close frame carrying status `1007`. The close is given one bounded flush window before `WsForceClose` takes over, so a peer that has stopped reading cannot convert protocol compliance into a hang. The close status is recorded in a dedicated field rather than the general error-code field, keeping the RFC 6455 status namespace separate from WinSock and internal codes, and it surfaces in diagnostics as `WebSocket close=1007`.

**Invalid outgoing text.** An isolated UTF-16 surrogate in caller-supplied text is rejected before any frame is built, and this deliberately does *not* fail the connection. Nothing was transmitted, the peer saw nothing, and the socket is healthy; RFC 6455 mandates failing the connection for text *received*, not for text the client declines to send. The rejection is therefore the least ambiguous failure the transport can produce — it cannot have partially executed — so it is reported to the caller as `WS_ERR_INVALID_UTF16` while the session continues.

Only the transport-layer codec moved. The discovery recorder still writes its log file through a stream object, which is the layer that abstraction belongs to: there the conversion is one stage of a text-to-file pipeline rather than a pure function pretending to be a stream.

## Bounded Pump Architecture

All native progress is driven through `WsPump`, a work-bounded state-machine step. Each pump call is capped by time, bytes, and call count (`WINSOCK_PUMP_MAX_MS = 10`, `WINSOCK_PUMP_MAX_BYTES = 262,144`, `WINSOCK_PUMP_MAX_CALLS = 16`). This is the central design change: receive, send, connect, and handshake progress are advanced cooperatively, but no single native call is allowed to monopolize the VBA host.

`SendAndReceive` still owns response correlation for one command ID, but it now does so around repeated bounded pump steps. If no data is produced, the loop yields briefly; if data is flowing, the loop drains it without artificial sleep so asynchronous events cannot bury the matching response. When the receive queue is empty, `ReadFromWinsock` waits on socket readiness with a bounded `select()` call (read and exception readiness, plus write readiness while a send is pending) instead of polling with `Sleep(1)`. Each wait is capped at `READ_WAIT_MAX_MS = 15`, no longer than one default Windows timer tick, so the bounded-pump architecture is unchanged, while arriving data wakes the reader immediately rather than at the next tick. A `select()` timeout simply returns to the next `WsPump`; only a `SOCKET_ERROR` falls back to `Sleep(1)`, and failure detection remains in the pump. The same bounded pump/`select()` loop also backs `IdleReceive`, the idle wait used between wrapper polls (Chapter 2): it enqueues completed events without returning them, so dispatch order is unchanged while arrival times stay close to the wire. A single `WsPump` completes at most `WS_MAX_COMPLETED_MESSAGES_PER_PUMP = 8` messages; when a pump stops at that cap, complete frames can remain in the user-space receive buffer while the kernel buffer is already empty, so `IdleReceive` repumps immediately instead of entering `select()`. Without this, each further batch of eight buffered events would wait for a readiness timeout (about one timer tick) and carry that delay into its arrival time.

## Request ID Management and Protocol Command Dispatch

The communicator still centralizes request ID generation (`GetNextRequestId`) and BiDi envelope construction (`id + method + params`). Ordinary command IDs live in `[100..ID_MAX]`. The lower band `[1..99]` is reserved: ID `2` is the fixed PostScript ID, IDs `[3..99]` rotate for application-heartbeat traffic, and ID `1` remains unused but reserved. Reserved-band replies are consumed internally at both receive sites, while id-less BiDi events remain application traffic and are eligible for buffering.

`SendCommand` continues to unify ID generation, JSON serialization, outgoing-size validation, send, receive, and response return. The outgoing `MAX_MSG_SIZE` guard remains in place to prevent accidentally sending a payload large enough to freeze the VBA runtime.

## Root-ID Classification and Late-Response Quarantine

Every receive site uses the same four-way classification: the response matching the command currently owned by `SendAndReceive`; a reserved system reply in `[1..99]`; a late or otherwise unknown root response ID; or an id-less asynchronous event. This prevents a command reply that arrives after its owner timed out from being mistaken for browser event traffic.

A nonmatching root response is discarded immediately, increments `DroppedLateResponsesCount`, and never consumes event-FIFO capacity. It still counts as evidence of peer progress and clears application-heartbeat suspicion. A direct new connection resets this counter together with the event-drop counter; a recovery reconnect preserves both counters and the complete queued-event FIFO so the final session summary covers the whole logical session.

## Low-Cost ID Extraction Without Intermediate Objects

`ExtractJsonId` still routes responses without parsing the whole JSON object. It scans the UTF-16LE byte view of the string, checks root-object depth, string state, escape state, and ASCII high bytes, and extracts only the root-level numeric `id`. This prevents nested payload fields from being mistaken for the BiDi response ID and avoids allocating a full JSON object merely to correlate one response.

## Receive-Side Size Cap and Identity Diagnostics

`MaxIncomingSize` remains the inbound safety valve inside the WinSock/RFC 6455 parser. The v4.6 default is **5 MiB (5,242,880 bytes)**, with a public minimum of 300,000 bytes and a hard maximum of 32 MiB. Once a text or binary message crosses the configured limit, the parser stops retaining the ordinary full body and drains the rest of that WebSocket message through its boundary. In parallel, a separate bounded diagnostic path retains only a small prefix and counts the total payload bytes observed.

At the final frame boundary, the communicator emits one critical identity diagnostic containing the total bytes observed for that message, the configured limit, the retained byte count, an ASCII-safe rendering of the retained prefix, and the number of adjacent `}{` JSON-object markers in that prefix. This makes recurring giant messages identifiable without allowing the diagnostic itself to become an unbounded memory cost. High-volume event streams such as `network.beforeRequestSent` can therefore remain available for investigation while oversized messages are drained safely rather than fully materialized in VBA.

v4.6 adds a **fast discard path** for payload bytes that are already known to be discard-only. Instead of repeatedly copying those bytes through the normal small receive buffer, the communicator may read them directly into a reusable buffer in chunks of up to 256 KiB. The optimization never crosses the current WebSocket frame boundary and still obeys the ordinary `WsPump` time, byte, and call budgets. It reduces `recv`/copy overhead for very large network events, but it does not change WebSocket ordering: a later command response still cannot overtake earlier bytes already present on the ordered stream.

## Chapter 2 — VBA Runtime Constraints and Anti-Freeze Measures

VBA’s classic weakness — the Office host becoming unresponsive — is addressed by eliminating blocking WebSocket receive from the transport core. The remaining task is to control where VBA may yield and where it must not yield. **A non-blocking transport is not the same thing as an always-responsive Excel UI.** With v4.4’s default `AllowUiPump=False`, a long synchronous correlation wait deliberately does not process Office messages, so the UI may temporarily look unresponsive even though native receive remains bounded.

## Guarded Command-Correlation Ownership

Inside `SendAndReceive`, the `m_isSendReceiving = True` flag marks that one command owns response correlation. In v4.4, that ownership can coexist with Office message pumping only when `AllowUiPump=True`: a dedicated `YieldCommandCorrelationUi` path breaks the receive wait into roughly 50 ms bounded slices and pumps Office between slices. During that yield, `m_isCommandUiYielding` is set and public command, transport, and lifecycle entries reject re-entry. With the default `AllowUiPump=False`, command correlation performs no Office message pumping, preserving the non-reentrant behavior.

## Lifecycle Re-entry Barriers

`StateChanged` is a synchronous advisory event, not a place from which transport operations may be nested. While its notification is running, `Connect`, `Disconnect`, `ForceClose`, `SendAndReceive`, `SendMessage`, and `GetMessage` reject or defer work. Subscriber errors are swallowed after an Immediate Window diagnostic so a faulty handler cannot interrupt socket cleanup.

Recovery uses the same discipline. `m_isRecovering` is acquired before any yielding work, only the recovery routine may authorize its internal reconnect, and `Disconnect` or `ForceClose` can cancel the backoff before native handles are rebuilt. These barriers turn deliberate `DoEvents` during recovery from an uncontrolled re-entry risk into a bounded lifecycle transition.

## Non-Blocking Native Pump Instead of Blocking Receive

The old WinHTTP path depended on a synchronous WebSocket receive. The current design replaces that with a WinSock state machine: `WsPump` advances connect, handshake, send, receive, frame parsing, ping/pong, and message completion in bounded slices. Each pump call has explicit work limits, so the transport can make progress without handing the VBA host to an unbounded native wait.

This changes the meaning of “anti-freeze”. The code no longer tries to rescue an already-blocked receive call; it avoids entering such a call in the first place. Timeouts now wrap the command-correlation loop above the socket rather than attempting to interrupt a blocking transport primitive.

`ReadFromWinsock` uses the same readiness policy through the correlation deadline. After each bounded `WsPump`, an empty receive queue waits with `WsWaitForSocketActivity` for at most `READ_WAIT_MAX_MS = 15`; when less time remains, the requested readiness wait is `CLng(remainingMs) + 1`. The final portion is therefore not busy-spun with `Sleep(0)`. This deliberately permits a boundary overrun of roughly one Windows timer tick rather than spending the final ~20 ms of short correlation slices spinning, which is especially important when `AllowUiPump=True` divides a long command wait into UI-yield slices. A readiness timeout is normal; the existing 1 ms sleep remains only as the fallback when the readiness helper itself cannot wait successfully.

## YieldExecution and InterruptibleSleep

`YieldExecution` remains the controlled wait primitive. Short waits use `SleepWinAPI`; longer waits are split by `InterruptibleSleep`. `YieldExecution` itself still suppresses ordinary `DoEvents` while `m_isSendReceiving` is active. When command correlation is explicitly allowed to pump the UI, it uses the separate guarded `YieldCommandCorrelationUi` path instead. v4.4 therefore keeps response correlation owner-aware rather than turning it into an unrestricted `DoEvents` region.

Since v6.1, the wrapper's wait heartbeats sleep through `IdleReceive` rather than `YieldExecution`. `IdleReceive` holds the non-yielding read guard, pumps the socket and waits on bounded `select()` until the requested time elapses, classifying completed messages exactly as `GetMessage` does but only enqueuing events. It never runs `DoEvents`. It falls back to `YieldExecution` whenever another path owns the receive side (`m_isReading`, `m_isSendReceiving`), during recovery, `StateChanged` notification, UI yields or termination, and when the communicator is not connected; a transport failure detected during the wait moves the communicator to `StateError` with a critical trace, as `ReadFromWinsock` does. Measured with no traffic, a 20-second `IdleReceive` used about 1% of process CPU.

The lesson from earlier timer-quantum behavior still applies: tiny sleeps inside a per-fragment hot loop can expand into large delays because Windows rounds sleeps to timer ticks. Frame assembly is therefore driven by bounded pump work, not by sleeping per fragment.

## PumpMessages — A Lightweight Message Pump

`PumpMessages` still runs only `DoEvents`, with optional throttling through `m_lastPumpTicks`. It exits immediately during `SendAndReceive`. The wrapper may call it while recording or during outer waits, but the communicator’s correlation loop remains protected.

## AllowUiPump — Explicit Opt-In Office UI Pumping

`AllowUiPump` is exposed through `BiDiCommandWrapper` and applies to guarded connection and command-correlation waits. The v4.4 default is `False`. That setting prioritizes non-reentrant synchronous execution, which means a long correlation wait such as `CallScript(safetyTimeoutMs:=600000)` may leave Excel looking unresponsive until a response or correlation timeout is reached.

```
' Default: preserve non-reentrant correlation waits
bidi.AllowUiPump = False
```

```
' Opt in when Office responsiveness during long waits is more important
bidi.AllowUiPump = True
```

With `True`, Worksheet events, ActiveX events, `Application.OnTime`, or other VBA callbacks may run while a command is waiting. The communicator rejects transport re-entry through its command/connect UI-yield guards, while the wrapper makes download, new-context, file-dialog, and navigation-status one-shot transactions mutually exclusive. A nested BiDi command can therefore be rejected with error 606 or a wrapper-side re-entry error rather than corrupting the outer transaction.

Lifecycle entries behave differently from commands. During a command-correlation yield, `Connect` returns `False`, and `Disconnect` and `ForceClose` return without doing anything; none of them raises 606, and the rejection is recorded only as a non-critical trace, so it leaves no evidence in the production configuration. During a connection-wait yield, `Disconnect` and `ForceClose` are deliberately accepted and cancel the pending connection attempt: after the yield, the connect loop observes that the state is no longer `StateConnecting` and exits without trying the IPv4 fallback.

**Callback constraint.** Code that runs inside such a yield must not call `Shutdown` or `ClearState` on the wrapper whose command is still waiting. For `Shutdown`, BiDi cleanup commands may be rejected with 606 inside best-effort handlers, so AutoClicker, Shadow Unlocker, download-behavior, file-chooser, body-collector, or subscription cleanup may not reach the browser. The wrapper-side state is still reset before transport teardown is attempted. If the final `ForceClose` / `Disconnect` is rejected because command correlation or a synchronous `StateChanged` callback still owns the communicator lifecycle, `Shutdown` detects that the communicator remains `StateConnected` or `StateConnecting`, emits a critical Immediate Window diagnostic when debug mode is enabled, and returns **without** setting `m_shutdownCompleted`. A later `Shutdown` or `Class_Terminate` call can therefore retry teardown after the outer command or callback has returned instead of becoming a permanent no-op.

`ClearState` behaves differently. If the waiting command owns an exclusive capture (download batch, new-context capture, file dialog, or navigation status), `ClearState` raises `ERR_REENTRANT_CAPTURE` before changing anything. Otherwise its browser-side releases are likewise rejected with 606; because the socket is still connected, the active subscription registry is retained rather than moved to deferred cleanup, but volatile wrapper state such as the main-context binding, completion-signal arms, and context caches is reset underneath the waiting command. `ClearState` does not set the shutdown-completed flag.

A stop button or timer callback should therefore set a flag and let the outer procedure call `Shutdown` or `ClearState` after the waiting command has returned.

The property is not a global switch for every Office pump in the system. Outer waits and recorder paths have their own pumping behavior; short `RecordEventsForSeconds` runs deliberately keep UI message processing available for discovery usability.

## Unified QPC-Based Timer API

QueryPerformanceCounter (QPC) remains the single timing source. `Class_Initialize` fails fast if QPC is unavailable. `NowTicks`, `ElapsedMs`, and `NowMs` all derive from the cached QPC frequency, so connection deadlines, send deadlines, pump budgets, and wait windows share a monotonic clock.

## Non-Yielding Read Guard

`m_isReading` is now a same-thread guard around non-yielding pump/dequeue work. It prevents nested receive paths from entering the WinSock parser simultaneously and is released through structured cleanup. Because native receive itself is non-blocking, this guard no longer needs to be a workaround for an indefinitely stuck WinHTTP read.

## FIFO Protection for the Event Buffer

The asynchronous event FIFO is bounded by both retained count and retained VBA-string bytes:

- `EVENT_BUFFER_MAX_COUNT = 2,000`
- `EVENT_BUFFER_MAX_BYTES = 33,554,432` (`32 MiB`, measured with `LenB`)

Before a new event is queued, the communicator removes the oldest events until both limits can be satisfied. A single event larger than the full byte budget is rejected without evicting the existing queue. Every discarded event increments `m_DroppedEventsCount`. In addition, the communicator performs a bounded top-level `method` scan on discarded event text and increments a purpose-specific loss counter for `browsingContext.contextCreated` / `contextDestroyed` / `navigationStarted`, `browsingContext.downloadWillBegin` / `downloadEnd`, or `input.fileDialogOpened`; an event whose method cannot be established is counted as `UnknownCriticalEventLossCount`. Reserved-band replies `[1..99]` are consumed internally, and late or unknown normal-band responses are counted separately in `m_DroppedLateResponsesCount`; neither category consumes this application-event budget.

Since v6.1, each FIFO item is a single `Array(message, arrivalMs)`, where `arrivalMs` is `nowMs()` at enqueue. Keeping text and arrival time in one item makes them inseparable through enqueue, eviction, dequeue, reset, teardown, and recovery-preserved queues; byte accounting still uses `LenB` of the message. `LastEventArrivalMs` exposes the arrival time of the most recently returned event: the enqueue time for a buffered event, or the read time for an event returned directly from the wire. It is valid immediately after `GetMessage`, `GetMessageNonBlocking`, or `TryGetParsedEvent` returns an event. A regression test that forces 500 evictions out of 2,500 events verified strictly increasing order, non-decreasing arrival times, and enqueue-time (not dequeue-time) stamps.

## Parsed-Event Admission and Queue Continuation

Completed event strings pass through a second, recorder-facing admission boundary. `TryGetParsedEvent` has an explicit three-state contract:

- `False` — no event was available;
- `True` with a parsed object — one valid event was consumed; and
- `True` with `parsed Is Nothing` — one event was consumed but rejected as too short, structurally irrelevant, oversized for recorder parsing, or malformed JSON.

The third state is deliberately distinct from an empty queue. It allows `ProcessRecorderQueue` to skip a bad event and continue immediately with the following event in the same batch. The compatibility `GetParsedEvent` method remains available for callers that understand only Object/Nothing.

Since v6.2 the same admission is also available in two steps. `TryGetEventText(rawMsg, dropReason, arrivalMs, …)` performs retrieval and the cheap admission checks (too short, oversized, no root method or id) without parsing, and returns the event's arrival time together with its text so the FIFO pairing of message and arrival time is preserved across the API boundary. `ParseEventText(rawMsg, parsed, dropReason)` performs the JSON parse through the communicator's event parser `ParseJsonText` (since v6.8; Chapter 7, "Event JSON Parser") and the malformed-event accounting. `TryGetParsedEvent` is now the composition of the two and keeps its three-state contract and loss accounting unchanged. The split exists so that the Recorder can decide, per event, whether a full parse is needed at all.

Recorder-side drops are counted separately as `DroppedParsedOversizeCount`, `DroppedParsedMalformedCount`, and `DroppedParsedFilteredCount`; `LastParsedEventDropReason` exposes the latest reason. Oversized and malformed parsed events also pass through the same bounded critical-event classifier, so loss of a lifecycle, download, or file-dialog event remains visible even when the event reached the FIFO but was rejected at the recorder-facing parse boundary. Direct connections reset these counters, recovery reconnects preserve them, and the critical session summary includes them together with asynchronous FIFO, late-response, and classified critical-event loss.

The "no root method or id" admission check is a literal search for `"method":` and `"id":`. A message that writes whitespace between the key and the colon is valid JSON but is rejected here and counted in `DroppedParsedFilteredCount`, which is not part of `TotalAsyncEventLossCount`. Current ChromeDriver and msedgedriver send compact JSON, so this has not been observed; the check is left unchanged in v6.8. A future fix should fall back to `TryExtractTopLevelEventMethod`, which already accepts that whitespace, only when the literal search fails.

## Chapter 3 — SPA (Single Page Application) Consensus Synchronization

To answer the question “when is loading actually complete?” on modern web stacks like React, Vue.js, and Google Wiz, we adopt an algorithm that confirms a “settled state” through the consensus of two independent observers.

## In-Browser Probe Injection

A monitoring probe, `window.__vbaIdleProbe`, is injected into each target JavaScript context. Its base `MutationObserver` watches `childList`, `characterData`, `attributes`, and the full document subtree. v4.4 also discovers reachable open ShadowRoots, attaches a MutationObserver to each one, and recursively scans newly added descendants for additional ShadowRoots. A `WeakSet` prevents duplicate observation. For a text-node mutation, the parent element is used when building the diagnostic XPath, so a text-only rewrite is reported as a useful element path rather than an unusable text-node location.

The probe separates activity timing from diagnostic deduplication. Every accepted mutation advances `lastMutationTs`, even when the same `DOM:` or `ATTR:` entry is already present in `changeList`. The list itself remains deduplicated and capped at 50 entries per status sample. Since probe version 44, mutations whose new path no longer fits are not silently discarded: the probe counts them (`changeDropped`) and keeps the first and last timestamps of dropped entries that qualify as content renders (`dropRenderFirstTs` / `dropRenderLastTs`, using the same content-render rule as the VBA side), and the status query returns and resets these values with the list. This prevents an aggressive `minStableMs` setting from declaring Stable while one node is still being rewritten repeatedly between polls.

## Fetch/XHR Prototype Hooks

`window.fetch`, `XMLHttpRequest.prototype.open`, and `XMLHttpRequest.prototype.send` are wrapped to expose browser-side request state. `inflightFetchCount` and `inflightXhrCount` are the formal pending values used by consensus and timeout escalation. A separate `inflightUrlCounts` map reference-counts each URL, so two simultaneous requests to the same endpoint produce a pending count of two while the operator-facing URL list contains one distinct key. Each completion decrements the URL count and removes the key only when its reference count reaches zero.

Requests matching the live `ignoreNetwork` patterns are excluded.

The hooks live in the page's window realm only. Fetch/XHR issued from a Web Worker is not counted, so `netIdle` can be true while worker-side API traffic is still in flight. This is a measured case, not a theoretical one: on Outlook on the web, draft creation and saving (`CreateItem`, `UpdateItem`) and attachment upload (`CreateAttachmentFromLocalFile`) are sent from a worker, and their `network.responseCompleted` events carry an empty `params.context`. Worker traffic is deliberately not added to the pending counts, because an empty-context request cannot be attributed to a tab and a resident worker would hold every wait open. Operations whose completion is worker-side are gated with explicit evidence instead: a DOM or visibility signal, or a network signal armed with `allowContextless:=True`. Counters and URL references are decremented on fulfillment, rejection, synchronous dispatch failure, and XHR `loadend`, with clamping at zero as a final corruption guard.

Probe repair uses generation tokens. Every newly installed Fetch or XHR layer captures the current generation; a stale layer that remains inside a page-provided Sentry, Datadog, or similar wrapper chain forwards the call without counting when its generation is no longer current. Repeated page wrapping and probe repair therefore cannot inflate the diagnostic pending count.

## State Detection via Property Descriptor Hooks

To capture value changes made by code that does not trigger a DOM event (for example, `element.value = "…"`), the probe obtains the Property Descriptor of `HTMLInputElement.prototype.value` and redefines the setter. The original getter and setter are preserved and invoked via `call()`, so normal behavior is retained. Unsupported or frozen descriptors fail locally and are reported through the probe-health contract rather than breaking the page.

## Probe Health, Repair, and Runtime Filter Revisions

The probe carries an internal version and reports health for the Fetch hook, XHR hooks, base observer, **ShadowRoot-observer capability**, and input-value descriptor. The mere presence of `window.__vbaIdleProbe` is not sufficient: a page framework may replace one hook while leaving the shell object intact. v4.4 therefore requires `shadowObserverReady` together with `versionOk`, `fetchWrapped`, `xhrWrapped`, `observerActive`, and `inputWrapped`; any missing, old, or unhealthy contract enters the bounded reinjection path.

Probe version 43 (v6.1) records `observeStart` (page epoch milliseconds) whenever the probe is installed or repaired, and each status sample returns it together with `performance.timeOrigin`. Mutations before `observeStart` in a document are outside probe observation. The status sample also maps the VBA monotonic clock to page epoch time from the query midpoint, with half the query round trip as mapping uncertainty. The version bump makes an existing version-42 probe fail `versionOk` once and be reinjected, as designed.

Probe version 44 (v6.2) adds the change-list overflow evidence described above. It was needed because the cap is reached routinely: on Outlook on the web, the save and close steps overflowed it in both measured runs, one with and one without recording (up to 90 dropped entries in one sample). Before version 44 such a sample could hide the only content render that followed a response and turn a rendered response into a false `[SPA-CONSENSUS-SUSPECT]`, and nothing in the log showed that entries were missing. As with version 43, an existing older probe fails `versionOk` once and is reinjected.

Probe version 45 (v6.3) removes the Shadow DOM signal paths that served the retired CSS-based `ArmShadowContentSignal` / `ArmShadowVisibilitySignal`: the probe-side CSS resolver (`shadowResolve`), `armShadowDomSignal`, `armShadowVisSignal`, and the `visKind` / `visPath` state. Visibility polling now evaluates only `visXPath`. The version bump makes a version-44 probe fail `versionOk` once and be reinjected; leftover members on a reused probe object are never called. A regression module verified on Edge 154 that content and visibility gates still control the wait: a control action without an arm settled in about 1 s, while armed actions whose DOM change was delayed by 2 s ended `STABLE` with `signal=dom:hit` and `signal=vis:hit`.

Probe version 46 (v6.4) restores the Shadow arm paths with an XPath per-root matcher. `shadowResolve(a)` takes a validated XPath scope chain and uses the same three root kinds as the element resolver (Chapter 4); `armShadowDomSignal` resolves the target through it, and `armShadowVisSignal` stores the chain in `visPath` with `visKind='shadow'`, so each visibility poll re-resolves through every reachable ShadowRoot until the first latch. `armVisSignal` sets `visKind='xpath'`. The Shadow content arm calls `obsDeep`, which attaches the one arm observer to the target and to every ShadowRoot inside it, and rescans the target subtree on each mutation batch so the roots of newly inserted hosts are added (a `WeakSet` prevents duplicate observation; the walk always descends). `sigRescan` is cleared by `armDomSignal` and `disarmSignal`, so a document arm never inherits the rescan hook. As before, an older probe fails `versionOk` once and is reinjected.

Since v5.1, Discovery diagnostics distinguish normal lazy initialization from loss of a probe that had already been verified healthy in the same document. `[SPA-PROBE-INITIALIZING]` / `[SPA-PROBE-READY]` describe first use or a newly replaced document and are not recovery failures. `[SPA-PROBE-UNHEALTHY]` / `[SPA-PROBE-RECOVERED]` are reserved for a probe that was previously healthy in that document and later became missing or unhealthy. Unverified samples contribute no stability evidence, and READY/RECOVERED restart the full confirmation window before STABLE can be reported. This distinction prevents ordinary post-navigation initialization from being misread as probe failure.

Idle-ignore filters are live configuration rather than injection-time closures. `AddIdleIgnoreSelector`, `AddIdleIgnoreNetworkPattern`, and `ClearIdleFilters` increment a VBA-side revision. Each browsing context records the revision last pushed into its healthy probe; the next preparation of an out-of-date context updates `p.selectors` and `p.ignoreNetwork` in place without rebuilding Fetch, XHR, or MutationObserver hooks.

Blank selector and network-pattern inputs are rejected at the public API boundary. Idle-ignore selectors remain CSS (unchanged in v6.4; they are the only CSS input of the public API) and are still guarded inside the browser because syntactically invalid nonblank selectors can reach `Element.closest`. The first exception adds the selector to `p.invalidSelectors`; subsequent mutations skip it without throwing again. The wrapper reports each invalid selector once per session as `[SPA-FILTER-INVALID]`, to both the Immediate Window when debug mode is enabled and the Discovery Log when recording.

## Dual Idle Consensus

Ideally, an SPA’s own application code would emit an explicit signal that “rendering is complete.” If that existed, waiting would be trivial. But when you’re dealing with arbitrary sites, you can’t count on that cooperation, and unlike classic navigation, the load event fires on the initial shell, so it doesn’t coincide with the state a user perceives as “the page is finished.” If no completion signal exists, the only option is to observe from the outside and re-infer completion — this wrapper’s design starts from that resignation.

And it is here that the design philosophy diverges fundamentally from Playwright’s auto-waiting. Playwright does not ask “is the page done?” It waits until the specific element you are about to act on satisfies actionability (attached to the DOM, visible, not moving in position across two consecutive frames, passing a hit test without being obscured by another element, and enabled) — the object of the wait is the target element, not the page, and what it waits for is the presence of a desired state. Because presence is decidable, a global indicator like networkidle is officially discouraged as flaky.

This wrapper, by contrast, cannot obtain a completion signal, so it has no choice but to ask “has the whole page gone quiet?” — a global quiescence — and what it waits for is the absence of activity. Absence cannot be proven (“no new requests will arrive” is unfalsifiable), so it can only be approximated with a sustained window plus a timeout; the consensus-window reset and the arbitration mechanisms described below all manifest as the cost of making that approximation hold.

Why deliberately take the road Playwright rejected? Playwright’s element-scoped approach assumes a test author who “knows what to wait for,” whereas this wrapper deals with arbitrary web apps and scraping targets that it neither wrote nor has tests for. In a domain where intent-based assertions aren’t at hand, observation-driven global-quiescence estimation is the practical solution that remains by elimination. The application emits no completion signal, and there is no element to name as the thing to wait for — under that dual constraint, robustness is bought through the consensus of multiple observations. That is the reason the consensus approach was adopted.

“Load complete” is defined, in principle, as the moment the following two conditions are satisfied and held together for a set duration (not an instantaneous intersection: the consensus state must persist for `minStableMs`; if activity is detected midway, the consensus window `stableStart` is reset):

1. The JS-side Fetch/XHR request count is zero.
2. The specified time (`minStableMs`) has elapsed since the last DOM change.

This is a two-observer consensus. `EvaluateSpaIdleCondition` forms its verdict from `netIdle = (inflightFetchCount = 0 And inflightXhrCount = 0)` and `activityStable = (the DOM-quiet duration has reached minStableMs)`. The URL collection is diagnostic only; it is not the authority for whether network work remains pending.

## Completion-Signal Gate — Reintroducing Presence into a Quiescence World

The Playwright comparison above framed this wrapper’s wait as an approximation of absence, adopted because no decidable presence condition is available for arbitrary sites. But sometimes one is available: the operator often knows exactly which DOM change, API response, or element appearance marks “done” for a given operation. The completion-signal gate injects that knowledge into consensus. When armed, the verdict becomes `netIdle ∧ domStable ∧ signalGateOpen`, so quiescence alone cannot complete the wait while the declared evidence is outstanding.

The API is a deliberate two-phase design — arm first, then let the next SPA-idle wait consume the arm — with one method per signal type:

- `ArmContentSignal` watches an existing XPath target subtree for child-list and character-data changes, optionally including attributes;
- `ArmNetworkSignal` latches a matching `network.responseCompleted`, regardless of HTTP status; and
- `ArmVisibilitySignal` repeatedly evaluates an XPath until an element becomes visible.

Multiple armed types compose with AND; a successful arm of the same type replaces the previous arm. A rejected arm leaves the previous arm of that type intact in both VBA and the browser, because the target is resolved and validated before the old observer is disconnected. Content arms reject a missing target or an invalid XPath. Visibility arms permit an absent or hidden target but reject an invalid XPath and a target that is already visible, because the latter would silently create an ungated next wait. Every DOM or visibility arm also fails when the SPA probe is unavailable in the target context. Since v6.4 `ArmContentSignal` and `ArmVisibilitySignal` accept `searchShadow:=True` (and an `Array` scope chain) and resolve the target through the probe's `shadowResolve`; v6.3 had removed the CSS-based `ArmShadowContentSignal` / `ArmShadowVisibilitySignal`. A Shadow content arm observes the target and every ShadowRoot inside it. One case is still missed: a ShadowRoot attached later to an element already inside the target, with no other mutation in an observed tree afterwards, because `attachShadow` produces no mutation record. A Shadow visibility arm re-walks every reachable ShadowRoot on each poll until it latches, so it is opt-in. `ArmNetworkSignal` needs no Shadow variant, because network-response matching is independent of DOM encapsulation.

Arming is an accuracy refinement, not a prerequisite for every SPA wait. With no active arm, `WaitForNetworkIdleSpa` remains an ungated `netIdle ∧ domStable` wait and `[SPA-WAIT-BEGIN]` / `[SPA-WAIT-END]` omit the `signal=` field. This fallback is intentional for discovery work: observe an ungated run first, use the resulting log to identify a concrete DOM, visibility, or network completion signal, then arm that evidence and re-run. The short-lived file-selection path follows this same observe → arm → re-measure cycle instead of failing before it can produce diagnostic evidence.

All active arms have one browsing-context owner. The first arm resolves an omitted `contextId` to the current main context and claims it; additional arms, the consuming SPA wait, and an explicitly scoped disarm must use the same context. This keeps the ordinary one-argument API simple while preventing a signal armed in one tab or iframe from being consumed by work in another.

Network matching first tests the URL pattern against the raw response URL (not the normalized Discovery key, so query values removed from the log, such as the value of `n=`, remain matchable) and then requires `params.context` to equal the owner context. A matching URL from another tab or an iframe with a different context never opens the gate. A response with an empty context (typically a Web Worker fetch) is rejected by default and accepted only when the arm was created with `ArmNetworkSignal urlPattern, allowContextless:=True`. The opt-in is deliberately narrow: it admits empty-context responses only, never a foreign non-empty context, and it cannot prove which tab owns the worker, so the HIT is logged as `ctx=(empty) | contextlessOptIn=true | attribution=unverified`. Another tab of the same application issuing the same request could satisfy the gate; the flag is intended for single-tab automation of worker-heavy applications. Like other arm state, the flag is consumed with the arm. The first rejected match for an arm emits `[SPA-SIGNAL-CTX-MISS]` with the expected and actual context; when the actual context is empty and the arm did not opt in, the line adds `hint=allowContextless-if-worker`, making a silent non-hit diagnosable.

Signal timing is type-aware. A DOM or visibility HIT detected during the wait resets `stableStart`; a network HIT that occurs during the wait is latched by the event handler and resets `stableStart` on the first polling cycle that observes it. If a network HIT already occurred before `[SPA-WAIT-BEGIN]`, the wait starts with a fresh stability window after that HIT, so no separate HIT reset is needed. In all cases, STABLE still requires the ordinary idle/DOM-quiet/probe conditions and the full confirmation window. Armed state is consumed one-shot on every wait outcome. As a general rule, consumption happens inside the SPA wait engine, so arms survive when no wait runs: an action that fails before synchronization, a call with `waitNetworkIdle:=False`, or a wait rejected before it starts (for example by the context-ownership check). Such arms carry into the next SPA wait unless `DisarmSignal` is called. The short-lived file-selection composite is a deliberate exception: its cleanup disarms the application-completion signal owned by that operation even when the operation fails before the trusted chooser-trigger click or before the final SPA wait begins. Composite operations that preserve an arm record the carryover as `[SPA-SIGNAL-CARRYOVER]` and, if it is hit during the operation, `[SPA-SIGNAL-CARRYOVER-HIT]`. Network matching occurs before recorder noise filtering. Likewise, a DOM signal uses its own MutationObserver on the armed target subtree, so idle-ignore selectors do not suppress it; a region excluded from idle detection can still serve as explicit completion evidence. If navigation destroys an armed DOM or visibility observer, `[SPA-SIGNAL-LOST]` is emitted and the local gate remains closed, so the wait fails safe instead of degrading to ungated success. This pre-wait path is the normal case for fast state-changing requests: on Outlook on the web the worker-side `UpdateItem` triggered by the "save draft" click completed about 0.2 s before the post-click `[SPA-WAIT-BEGIN]`, and an arm placed immediately before the click still opened the gate (`signal=net:hit`).

The Discovery diagnostics preserve the distinction between observation and attribution. DOM/visibility HITs are poll-detected; network HITs are event-triggered and therefore do not have an exact DOM-quiet sample at the event instant (`quietAtHit=unknown`). `[SPA-NET-TO-CONTENT]` reports, for an armed network HIT that occurred after `[SPA-WAIT-BEGIN]`, the earliest retained content mutation at or after the response's completion lower bound, judged with the interval model below. Mutations under `<head>` or `<title>` are excluded from content-render detection, `observedMs` remains only the VBA-side HIT-to-poll observation delay, and the record keeps `owner=not-asserted`: temporal ordering does not prove that the response caused the render. For DOM signals, `count=` is the cumulative number of `MutationRecord`s observed on the single target subtree resolved at ARM until the polling cycle that first detects the HIT; it is not an element count, rendered-row count, page-wide mutation count, or an ownership claim. DOM ARM lines record `attributes=true|false` so attribute participation is explicit.

## Network Completion Interval Model (v6.1)

A network response has no single observable completion instant on the client side. `request.timings.responseEnd` in `network.responseCompleted` behaves as header receipt: for small bodies it matches the page's own Resource Timing within a few milliseconds, but for streamed bodies it can precede the completion event by many seconds (up to about 15 s measured on Google Flights `GetShoppingResults`). The completion event itself also reaches the client late: with the socket continuously observed, events still arrived 5–235 ms after `responseEnd`, and in one case the page had already rendered from the response about 20 ms before its event reached the socket. No amount of client-side speed can turn either clock into the true completion time.

v6.1 therefore treats completion as an interval `[lo, hi]` in page epoch milliseconds, taken when the event is dispatched:

- `lo = request.timings.timeOrigin + responseEnd`. It comes from the browser network clock, which read 1.8 ms earlier than the page clock on median (at most 7.9 ms) in measurements, so it is a safe lower bound.
- `hi = LastEventArrivalMs` mapped to the page clock plus the mapping uncertainty. It is an upper bound because `responseCompleted` is emitted after completion. `IdleReceive` keeps it close to the wire during waits; periods in which VBA drains a large FIFO backlog without reading the socket only widen the interval.
- An unavailable side is unbounded (`0`). If `lo > hi`, the interval is contradictory; `hi` is dropped, so the result can be BEFORE or INDETERMINATE but never AFTER.

Render times are page epoch values (`timeOrigin + changeTimes[path]`) of content mutations. Because the probe keeps only the latest change time per deduplicated path, a render can appear later than its first physical mutation; delay upper ends may therefore be conservative. Dropped content mutations reported by probe version 44 enter the same render evidence under the path `DOM:(overflow)` at their first and last dropped timestamps; because intermediate dropped times are not kept, the earliest render at or after `lo` can be approximated when an overflow straddles `lo`. A render is BEFORE the response when it precedes `lo`, AFTER when it follows `hi`, and INDETERMINATE inside the interval.

Render timing history — the latest content-render time, the render ring used by `[SPA-NET-TO-CONTENT]`, and the probe observation start — belongs to one browsing context. When an SPA wait targets a different context from the previous render-evidence context, that history is discarded at wait start, so a render observed in another tab or frame can neither turn a SUSPECT into INDETERMINATE nor be reported as the render for this context's response. Within the same context the history is retained across waits, including across that context's `load` / `domContentLoaded`. The VBA-to-page-epoch clock mapping is kept, because it relates two clocks rather than recording render ownership.

At STABLE, every tracked JSON/API response seen **in that wait's browsing context** is judged against the latest observed content render. `network.responseCompleted` remains globally recorded for Discovery coverage, but a JSON/API response enters the render-evidence set only when its `params.context` matches the active wait/evidence context:

- **RESOLVED** — render after `hi`. No line is written.
- **INDETERMINATE** — render inside `[lo, hi]`. Written as `[SPA-CONSENSUS-UNRESOLVED] verdict=INDETERMINATE`.
- **UNOBSERVED** — no render at or after `lo`, but the completion may precede probe observation (`lo` unknown or earlier than `observeStart`). Written as `[SPA-CONSENSUS-UNRESOLVED] verdict=UNOBSERVED`.
- **SUSPECT** — no render at or after `lo`, and the whole interval lies inside probe observation. Written as `[SPA-CONSENSUS-SUSPECT]`; SUSPECT takes precedence over the unresolved verdicts for the wait.

UNRESOLVED is a normal diagnostic result, not a failure and not a suspicion. Only SUSPECT reserves the one-wait carryover hint (`[SPA-CARRYOVER-NOTE] reason=prev-wait-suspect`). The reservation stores the browsing context that produced the SUSPECT. It can arm only the **immediately following wait in that same context**; if the immediately following wait targets a different context, the reservation is consumed without arming and is not retained for a later return to the original context. A `browsingContext.load` or `browsingContext.domContentLoaded` event clears the tracked JSON evidence and carryover state only when its `params.context` matches the current render-evidence context. Loads in unrelated tabs or child frames remain globally logged but do not erase the active wait's evidence.

`[SPA-NET-TO-CONTENT]` uses the same interval. It selects the earliest retained content mutation at or after `lo` (after `hi` when `lo` is unknown), including mutations polled before the HIT was dispatched, and reports `relation=AFTER|INDETERMINATE`, `delayMs=min..max` (completion-to-mutation delay; `min` is 0 when INDETERMINATE), and `widthMs=hi−lo` (`unbounded` when a side is missing). A multi-second width is not an error: it states how little the network event can say about render causality for that response.

The previous single-timestamp model mapped the time VBA dispatched the event into the page clock. Because dispatch can lag arrival by tens to hundreds of milliseconds, it erred in both directions: it reported SUSPECT for responses that had rendered (Main07 `metadata/application`) and missed responses whose only content mutations preceded the response by about 120 ms (Main08 `batchexecute`). All four verdicts were confirmed on the production build against live sites.

## Branching when consensus is not reached (inside MasterWaitEngine)

When the polling loop reaches its timeout, the escalation decision is based on the last formal Fetch/XHR counts, not on whether a URL string happened to be available. If `inflightFetchCount > 0` or `inflightXhrCount > 0`, the timeout is remapped to `ERR_CONSENSUS_HALT` (`vbObjectError + 1010`) and propagates through `TrySyncPhase` to halt the caller.

The distinct URL keys remain valuable evidence and are printed when available, but an empty URL list cannot downgrade a real pending count. The HALT message therefore always reports the Fetch and XHR totals and may explicitly indicate that URL details were unavailable.

When both formal counts are zero, the timeout is classified as DOM-only or signal-related best-effort synchronization failure and retains the ordinary timeout path. After an action has completed, `TrySyncPhase` absorbs every post-action synchronization failure except `ERR_CONSENSUS_HALT` and `ERR_SESSION_CONTINUITY_LOST` (`vbObjectError + 1030`, Chapter 18). The absorbed set includes DOM-only timeouts and infrastructure failures such as probe loss, protocol errors, and context loss. Raising them would invite the caller to treat an already-performed action as failed and replay it. The failure is instead recorded in `LastSync*` (Chapter 9). Session-continuity loss is different: the action still completed, but the transport can no longer confirm anything, so it is recorded in `LastSync*` and then re-raised. The navigation settlement path is narrower and propagates only `ERR_CONSENSUS_HALT` (Chapter 16).

## Four-Way Wait Outcomes (SPA-WAIT-END)

Every recorded SPA-idle wait closes in the Discovery Log with exactly one of four outcomes: STABLE (consensus reached), HALT (logical timeout with outstanding Fetch/XHR counts, escalated as `ERR_CONSENSUS_HALT`; pending URL details are diagnostic and may be unavailable), TIMEOUT (logical timeout with no outstanding formal network count, including a `WaitBudgetExhausted:` command whose remaining wait budget was consumed), or ERROR (a non-timeout failure such as probe loss, an untagged command-correlation timeout, a protocol error, or a socket error). v6.7 deliberately normalizes **only** wait-budget exhaustion to 504; an ordinary 604 that occurs while budget remains stays ERROR. This preserves the rule that infrastructure failures are never disguised as tuning problems. On the post-action path, an ERROR is still absorbed rather than raised, except for `ERR_SESSION_CONTINUITY_LOST`; the distinction survives in the Discovery Log and in `LastSyncErrorNumber`. The DebugMode Immediate Window warning emitted by `TrySyncPhase` uses one generic text that suggests extending the idle timeout regardless of cause, so triage should rely on the recorded outcome and error number, not on that warning text.

`[SPA-WAIT-END]` also carries `changeOverflow=`, the number of change-list entries the probe dropped during that wait (v6.2); a nonzero value means that wait's `[SPA-ACT]` lines are incomplete, although the dropped content renders were still counted as render evidence. Since v6.7, `stableWindowMs` starts only when a verified poll first observes the complete condition as satisfied: zero Fetch/XHR count, sufficient browser-side activity quiet, and every armed signal gate open. That first qualifying poll establishes the sampled start and **cannot** itself complete the wait; a later qualifying poll must observe at least `minStableMs` since that start. A false condition or explicit reset (signal HIT acknowledgement, probe READY/RECOVERED, navigation reset, or detected probe-health loss) clears the sampled window. Consequently, unsampled time before the first qualifying poll is never credited. The measure is still not an exact physical dwell time because the real condition may cross its threshold between polls. Probe-health fields remain fail-safe evidence: unverified samples contribute no stability evidence.

## v6.7 Wait Deadline Semantics and Remaining Verification Gaps

`MasterWaitEngine` converts `maxTimeoutMs` into an absolute `waitDeadlineMs`. Command-producing segments temporarily publish that deadline through private state (`m_commandDeadlineMs`), and `ExecuteBiDiCommand` recomputes the remaining budget before every send and recovery attempt. This automatically covers indirect commands such as `browsingContext.getTree`, `script.getRealms`, probe injection/query, URL reads, and HUD work without adding budget parameters to the public API. `WaitHeartbeat` runs with no command deadline by design so Office callbacks cannot inherit the wait's budget. If waits nest, `EnterCommandDeadline` keeps the earlier deadline. Cleanup restores the previous deadline on every exit path, including the error handler.

A command whose normal timeout is longer than the remaining wait budget is capped to that remainder. If the capped correlation wait expires, or the budget is exhausted before a retry can be sent, the 604 description is tagged `WaitBudgetExhausted:`. A capped correlation timeout does not run the extra liveness probe; an uncapped timeout may run one only within the remaining budget. Recovery backoff is capped the same way, and if the backoff consumes the remainder, context refresh and re-dispatch are skipped. Only tagged budget exhaustion is converted to logical timeout 504 by the wait. The original command/recovery description is retained after the logical-timeout text.

The decision order is intentional: (1) a sampled success returns SUCCESS, even if its response reaches VBA just after the nominal deadline; (2) an untagged error keeps its original error number; (3) tagged wait-budget exhaustion becomes 504; (4) an unmet condition whose outer deadline expires becomes 504. `ERR_SESSION_CONTINUITY_LOST` (1030) has priority over timeout where it is observed and is never normalized to 504. `SetWaitDeadlineError` also checks continuity before finalizing 504. The ordinary `WaitHeartbeat` continuity path was exercised; the exact race in which continuity is lost at the instant `SetWaitDeadlineError` runs remains code-reviewed but not directly reproduced.

The deadline is intentionally bounded rather than mathematically hard at zero overrun. `WaitHeartbeat` has a minimum wait granularity of about 50 ms, a response that proves success may finish by roughly one protocol round trip after the deadline, and exhausted-wait HUD removal may use up to `WAIT_CLEANUP_GRACE_MS = 250` ms of best-effort cleanup time. `WaitForUrlStability` does not use `MasterWaitEngine` and is outside this contract.

Regression measurements on Edge confirm the previously failing cases: a 2500 ms unsampled gap with `minStableMs=1000` completed in 2633 ms before the fix and 3813 ms after it; long-task waits with 1000/2500 ms budgets ended around 1.0/2.5 s; T1b forced the probe query itself to consume the remaining budget and produced tagged 604→504 with `PeerLiveness=not-probed(wait-budget)`; T2 exercised deadline-edge success; T4 exercised frequent navigation; and T4c forced context recovery under the wait deadline. In T4c A-short, one recovery attempt was cut off by the remaining budget and returned 504 in 1018 ms with `WaitBudgetExhausted: during recovery | trigger=... Environment desync (Context Lost)`. A-long entered recovery, succeeded on the new document, and later reached the 4000 ms logical deadline at 4074 ms. On real sites, Main07 (ServiceNow) and Main04 (manual login wait) each entered this recovery during a navigation and continued normally. In v6.6 the `WaitMode_UrlContains` branch let the `GetCurrentUrl` protocol error propagate, and `ExecuteIsUrlContains` has no handler for it, so a wait for the very navigation it watched could fail intermittently with `[unknown error] Inspected target navigated or closed`.

Two narrow observations remain explicitly unmeasured: the `SetWaitDeadlineError` continuity-loss race described above, and the user-visible latency effect of main-context `locateNodes` polling when Chromium returns `Inspected target navigated or closed` and the new recoverable classification adds the recovery backoff.

## Operator response

On a CONSENSUS HALT, the Immediate Window reports the formal Fetch/XHR counts and up to ten distinct pending URL keys when available.

- If the remaining traffic is analytics, beacon, font, or similar noise, add a pattern with `AddIdleIgnoreNetworkPattern`.
- If it is a legitimate slow API, extend `maxTimeoutMs` only after ruling out a stalled request.
- For continuing DOM noise such as clocks or carousels, use `AddIdleIgnoreSelector`.
- `[SPA-FILTER-INVALID]` means an ignore selector was rejected inside the page and is not suppressing anything; correct or remove it.
- `[SPA-SIGNAL-CTX-MISS]` means the URL matched but the response belonged to another or empty browsing context; align the arm, action, and wait context rather than widening the timeout. When the actual context is empty (`hint=allowContextless-if-worker`), the response came from a Web Worker; if the application's completion evidence is worker-side, re-arm with `allowContextless:=True` and accept that attribution is unverified.

## Synchronous SPA Interlock

The main action pipeline implements a BiDi-specific interlock based on `waitNetworkIdle`, the browser-side Fetch/XHR counters, DOM quiet, and `minStableMs`. This provides a strong best-effort synchronization baseline for Ajax-driven transitions. Exact operation-specific completion is not claimed from quiescence alone; when the caller knows the decisive response, rewrite, or appearance, the completion-signal gate is the mechanism that turns that knowledge into a hard precondition.

## Predictive Probe Recovery

Conventional recovery waits for repeated missing-probe polls before reinjection. By subscribing to `browsingContext.navigationStarted`, the wrapper records a one-shot navigation hint for the matching context. Once the ordinary query confirms that the probe is missing, old, or unhealthy, that hint bypasses the staged missing-count delay and triggers immediate repair. It does not remove the status query; it removes extra passive recovery cycles.

Health covers the version, Fetch wrapper, XHR open/send wrappers, base MutationObserver, ShadowRoot-observer capability, and input-value descriptor. Repair disconnects the old document and ShadowRoot observers and rebuilds the damaged hooks. Fetch/XHR generation tokens make old probe layers passive, so repair remains diagnostically exact even when page instrumentation keeps its own wrappers outside the current probe. Context-ID matching prevents an unrelated iframe navigation from consuming the hint, and per-context filter revisions are invalidated when navigation replaces the document.

## Chapter 4 — JavaScript & Browser Engineering

The language and synchronization gap between VBA and the browser is bridged with a custom watchdog and advanced DOM manipulation techniques.

## The JS Delegation Strategy

Everything in this chapter follows one top-level decision: ordinary request/response interaction JavaScript is concentrated in `script.callFunction` and routed through `Me.CallScript`. A multi-step interaction (find, measure, scroll, click, validate) can therefore execute in one browser dispatch, with a flat JSON-shaped result returned to VBA. BiDi acts as the transport and the browser’s JavaScript engine performs the high-frequency work. There are deliberate infrastructure exceptions: the persistent SPA probe is installed with `script.evaluate`, the Shadow DOM unlocker and AutoClicker use `script.addPreloadScript`, and teardown-only best-effort work may use `PostScript`. Those are protocol-management paths rather than ordinary interaction methods.

## Safety Shell (An Autonomous Browser Watchdog)

JavaScript sent through `CallScript` is wrapped by `WrapInSafetyShell`, where the execution task and a `setInterval` watchdog compete through `Promise.race`. The watchdog can detect a cooperative asynchronous task that keeps yielding to the browser event loop but stops calling `hb()` for longer than the configured timeout. It **cannot** pre-empt a synchronous event-loop-blocking loop such as `while(true){}` because the watchdog timer itself cannot run in that situation. The authoring contract therefore forbids synchronous blocking loops and requires long work to yield with `await`.

`WrapInSafetyShell` generates the following structure:

- Wraps everything as an async function.
- An `_la` variable holds the last-activity timestamp.
- An `hb()` closure is a lightweight function that simply updates `_la` to `performance.now()`.
- `_tk` (the task) and `_wd` (the watchdog) compete via `Promise.race`.
- The watchdog checks `performance.now() - _la > _t` on a 100 ms `setInterval`. The monotonic page clock keeps a wall-clock adjustment from firing or suppressing the watchdog.

A design where the result always passes through a single JSON-stringification point means the VBA-side `UnwrapSafetyShell` function receives a consistent envelope. `undefined` is converted to `null`, preventing loss of the value key. One subtlety is critical: `Promise.race` does not cancel the losing `_tk()` task. If the watchdog wins, browser-side work may continue after VBA receives error 517. The wrapper therefore classifies 517 as an ambiguous outcome and prevents automatic re-execution of state-changing actions.

## Heartbeat Closure (hb())

Calling `hb()` inside a JS wait loop updates the last-activity timestamp within the shell. This tells the watchdog that “processing is proceeding normally,” protecting legitimate long-running tasks. `hb()` is provided by the `WrapInSafetyShell` closure — it is not passed in as an argument: writing `const hb = arguments[0]` would overwrite the actual parameters (e.g., `sharedId`).

## Universal Hybrid Input Engine (Case “input_keys”)

An auto-detecting hybrid input engine that deflects the “field-swap phenomenon” on ultra-high-frequency SPA sites built on frameworks like Google Wiz, while still performing stable input on ordinary websites.

**Phase 0 — Stability check:** In Google Wiz/Lit structures, the moment you click the initially visible INPUT, the framework destroys that element and generates a “real input INPUT” behind the scenes. After clicking, the engine polls `document.activeElement` at 15 ms intervals and only confirms the target once the same element matches twice in a row.

**Phase 1 — Safely clearing the existing value:** On the confirmed input element, the existing value is removed through selection, `execCommand('delete')`, and, when needed, `execCommand('forwardDelete')`, with 80 ms asynchronous settling intervals. If a value still remains, the engine falls back to direct assignment plus a bubbling `input` event before continuing.

**Phase 2 — Character-by-character insertText:** Text is inserted one character at a time. The confirmation loop also monitors the active element; if the framework swaps the element mid-input, it re-binds immediately.

**Phase 3 — Defensive validation:** After insertion, the browser-side code verifies that a non-empty requested string produced a non-empty value whose length is at least the requested length. If the framework silently rejected or truncated the entry below that threshold, it throws `Wiz Input Validation Failed`. This is a length-based guard, not a full byte-for-byte equality assertion.

## Recursive Shadow Target Resolution

Since v6.3 Shadow element lookup takes XPath, and since v6.4 it is selected with `searchShadow:=True` on the ordinary element APIs instead of a separate method family. The deep-search contract of earlier versions is kept — the caller does not need one locator per ShadowRoot boundary — but the per-root matcher is now the browser's native XPath engine instead of `querySelector`.

One `script.callFunction` performs the whole search. A recursive function `fd(root, xpath)` first evaluates the XPath in `root` and, if nothing matches, enumerates the root's elements with `querySelectorAll('*')` and recurses into every reachable `shadowRoot`. That enumeration is internal; the caller never writes CSS. A shallower root therefore wins over the roots nested inside it, as in the earlier CSS resolver. An array chains scopes: each next XPath is deep-searched from the previous match's ShadowRoot, or from the element itself when it owns none. The resulting node is returned as a `sharedId` and bypasses `CallScript`, because the Safety Shell would JSON-stringify a node result.

```vb
bidi.ExecuteClick "//*[@id='utility-sign-in']//button", searchShadow:=True
bidi.ExecuteClick Array("//my-dialog", "//button[@id='save']"), searchShadow:=True
```

The only engineering problem is that `document.evaluate` rejects a ShadowRoot (a `DocumentFragment`) as the context node with `NotSupportedError`. The per-root matcher `m(root, xpath)` therefore distinguishes three root kinds:

| Root | Evaluation |
| :--- | :--- |
| `Document` (nodeType 9) | the XPath as given |
| `ShadowRoot` (nodeType 11) | `'..' + xpath`, with the root's `firstChild` as context node |
| `Element` (array chain without a ShadowRoot) | `'.' + xpath`, with the element as context node |

The context-node type check applies only to the initial context node, so the parent step from the first child lands on the ShadowRoot and the rest of the path is evaluated from there. Because `//x` abbreviates `/descendant-or-self::node()/child::x`, prefixing `..` replaces the leading root step with the ShadowRoot, which keeps positional predicates such as `//li[1]` exact. Only element nodes are returned (`nodeType === 1`); an XPath that selects a text node reports not found.

The approach depends on browser behavior rather than on a specification guarantee, so `ProbeShadowXPathSupport` checks it on the current page: it attaches a temporary host, evaluates four cases, removes the host, and returns JSON. On Edge 154 it reported `shadowRootAsContext=rejected:NotSupportedError`, `parentStepIntoShadowRoot=ok` (the required result), `slotTextMatch=notmatched`, and `absolutePathScope=shadowTree`. The last value means that an unprefixed absolute path evaluated from inside a ShadowRoot is scoped to that shadow tree rather than to the document; the `..` prefix does not depend on that behavior, and the observed scoping keeps absolute subpaths inside predicates within the same root.

The public contract is checked in VBA before polling starts, so contract errors are never retried:

- each XPath must be one location path starting with `/`; expressions starting with `(` and top-level unions (`|`, outside quotes, brackets, and parentheses) are rejected, which also rejects CSS selectors passed by mistake;
- a syntactically invalid XPath raises the JavaScript exception immediately (`ERR_JS_EXCEPTION`) instead of polling until the search timeout.

Two limits follow from evaluating each XPath within one tree: `ancestor::` stops at the ShadowRoot boundary, and string values (`.`, `text()`) do not include text assigned through `<slot>`. Predicates on an element's own text, including `text()`, `normalize-space()`, and `contains()`, behave as in the normal DOM.

`searchShadow:=True` selects the locator kind `ElementLocatorShadowXPath`; the default selects `ElementLocatorXPath` (`browsingContext.locateNodes`). Every element Core already takes the locator kind and resolves through `ResolveElementSharedId`, so stale-element re-resolution and the input path re-resolve through the same function, and the public entry points only choose the kind. `SelectElementLocatorKind` rejects an `Array` without `searchShadow:=True` and `requireUnlocker:=True` without it before any search. Errors from Shadow searches pass through `ReraiseShadowPublicError`, which adds the Unlocker diagnostic to a Shadow not-found result; XPath errors are re-raised unchanged. In `ExecuteDownloads` the outer `Array` keeps its meaning of a trigger list, so a scope chain for one trigger is a nested `Array` (`Array(Array("//my-panel", "//a[@id='dl']"))`). Capture transactions click their trigger with `PerformTrustedClick`, whose hit test already descends through `shadowRoot.elementFromPoint` and climbs `getRootNode().host`, so a topmost Shadow trigger receives a native pointer click. When the trigger is not topmost, `ExecuteOpenNewContext` and `ExecuteSetFileSelectionViaDialog` refuse the click and `ExecuteDownloads` falls back to a synthetic one (Chapter 9, "Click Strategy"). `ExecuteWizSelectDropdown` applies `searchShadow` to its trigger; its option search has always walked document and Shadow DOM.

Two test modules verified the resolver on Edge 154 against a five-level nested DOM (15/15 checks) and against closed/open/closed roots exposed by the Global Shadow DOM Unlocker (8/8). In v6.4 a third module verified native pointer clicks on Shadow triggers for the three capture transactions (4/4, `isTrusted=true`).

## Visible-First Selection in the Shadow Resolver (v6.5)

When the action prefers a visible target (Chapter 11, "Visible-First Candidate Selection"), `TryResolveShadowElementSharedIdOnce` sends a second function variant. Intermediate steps of a scope chain resolve hosts with the same `fd` and no visibility check, because a host often uses `display:contents` and has no box of its own. The final step lists candidates with `fa` in `fd`'s order: the root's own matches in document order, then every ShadowRoot reached through `querySelectorAll('*')`, depth first. A root contributes only when its first match is an element, as in `fd`, so the first candidate is always the node `fd` would return. The function returns `[node, matched, checked, chosen]`: the first visible candidate among the first 50, or the first candidate when none is visible. When visible-first is off, or for readers, the request is identical to v6.4.

Two costs follow. `fa` walks every reachable ShadowRoot even when an early root already matches, so this path does more work than `fd`. A v6.6/v6.7 local fixture placed the target in the final root and measured 10, 100, 400, and 1000 ShadowRoots (three repetitions each): end-to-end resolve/click averages were 70.3, 28.6, 26.0, and 28.6 ms respectively. The first case includes warm-up cost, and the measurement does not isolate `fa`'s micro-cost, but no practical degradation was observed through 1000 roots.

Since v6.7 the shared visibility predicate tests `inert` through flat/composed ancestry instead of DOM-only `closest()`: it follows `assignedSlot`, then `parentElement`, and crosses a ShadowRoot through `getRootNode().host`, with a visited-set guard. A fixture whose first Shadow candidate lived under an **outer** `inert` ancestor reproduced the old error (`closest('[inert]')` returned null and input failed with `ACTIVE_INPUT_NOT_STABLE`); after the change visible-first chose the second active candidate and completed the input. The closed-root Unlocker fixture was then rerun and still passed visible-first, AutoClicker, and DOM-arm behavior.

The earlier local fixture also verified the general rule on Edge with synthetic and trusted clicks (20/20 each): hidden-then-visible in one root picks the visible match; visible-then-hidden and hidden-then-hidden pick the first match, the latter being the v6.4 node; a `display:contents` intermediate host and two nested hosts resolve to the visible final target; a deep search without a scope chain picks a visible match in a later root over a hidden match in an earlier root; and `PreferVisibleMatch = False` restores the first match. With trusted clicks every visible choice was on-target, and only the two hidden targets produced `[TRUSTED-HITTEST] reason=zero-box`.

## Shadow Search in Browser-Side Scripts

The AutoClicker preload and the SPA probe evaluate the locator inside the page rather than through `ResolveElementSharedId`, so v6.4 embeds the same per-root XPath matcher in both. A validated scope chain is passed as a JSON array literal (`BuildShadowXPathJson`, applying the same contract checks as the element resolver).

The AutoClicker registers a Shadow locator under the key `S|<json array>` with the browser guard key `shadow|<json array>`, so a document XPath and a Shadow chain for the same text coexist as separate registrations. In `shadow` mode the preload finds the target with the recursive matcher (`mt` per root), observes the document and every open ShadowRoot, rescans on every mutation batch, and polls every 100 ms until its timeout so that roots attached later by `attachShadow`, which produces no mutation record, are still seen. This is the v6.2 mechanism with the per-root `querySelector` replaced; its cost — a full walk of every reachable ShadowRoot per batch and per poll until the click or the timeout — applies only to Shadow registrations. A syntactically invalid XPath never matches, as in document mode.

The arms use the probe-side `shadowResolve` described in Chapter 3. Closed roots are reachable only when the Global Shadow DOM Unlocker opened them. v6.7 regression testing verified the Unlocker path with a closed-root fixture: the root was exposed as open, visible-first chose the intended visible duplicate, the AutoClicker fired once, and a Shadow DOM arm observed the expected content change.

## Global Shadow DOM Unlocker

Using the W3C standard `script.addPreloadScript`, v4.4 installs a generation-guarded wrapper around `Element.prototype.attachShadow` before future documents run page script. While the current generation is enabled, the wrapper preserves the caller’s other initialization options but forces `mode:'open'`, calls the original function with `Reflect.apply`, and notifies the SPA probe so the new ShadowRoot can be observed immediately. The original function is retained only inside the generation state/closure; no extra public property is added to `Element.prototype`.

The generation state is stored under `Symbol.for('seleniumvba.bidi.shadow_unlocker.v44')`. A newer generation disables an older one, and Shutdown performs three best-effort containment steps while the BiDi session is still reachable: remove the tracked active preload, restore the active `attachShadow` wrapper in current realms when it still owns the prototype slot, and register a higher-generation **inert preload**. That inert generation is deliberate hard-reset insurance for an older `script.addPreloadScript` whose response may have been lost and whose script ID is therefore unknown. A later successful enable supersedes the inert generation.

This mechanism affects ShadowRoots created **after** the hook is active. A root that was already created as truly closed before the unlocker ran cannot be retroactively opened. Because preload scripts apply only to documents created after registration, a document that already existed at `ConnectTo` keeps native `attachShadow`; v6.3 testing confirmed this (closed roots stayed hidden in the pre-existing `about:blank` document and were exposed after one navigation). Such a page must be reloaded before its closed roots can be reached. `ConnectTo` enables the unlocker on a best-effort basis by default; `requireShadowUnlocker:=True` makes failure part of atomic connection initialization.

## Chapter 5 — Context Management and Navigation

Implementing the “compass” that navigates complex iframe hierarchies and multi-tab environments without state inconsistency.

## Recursive Frame Search (Stack Guard)

When searching for a specific contextId within the massive hierarchy returned by `browsingContext.getTree`, we use `RecursiveFrameSearch`. Limiting the search depth to a maximum of 20 prevents stack overflow (Error 28) caused by complex site structures. If Error 28 occurs, it is caught with the StackGuard label, returning an empty string to terminate safely.

## Stateless ID Addressing and Pinned Main-Context Ownership

We abolished the SwitchTo (stateful switching) method heavily used in legacy Selenium. Commands receive an explicit `contextId`, while an empty value resolves through the wrapper’s **pinned main-context** contract. When the wrapper is unbound and exactly one top-level context exists, that context is pinned automatically. When more than one top-level context exists, automatic selection is rejected and the caller must use `SetMainContextId` explicitly.

Once pinned, the main context is not silently replaced. The binding is a three-state contract — unbound, pinned, and lost — and the distinction between the last two is deliberate. If `browsingContext.contextDestroyed` reports that the pinned main context was destroyed *without the wrapper having asked for it*, or a later tree reconciliation proves it no longer exists, the wrapper enters `MainContextLost`. Operations that rely on the main context — an omitted `contextId`, `GetMainContextId`, or `UpdateMainContextId` — then raise `ERR_MAIN_CONTEXT_LOST` until the caller explicitly pins a surviving top-level context; operations that name an explicit surviving context continue to work. That independence is preserved during stale-element recovery and post-action / post-navigation synchronization: an operation explicitly targeting a non-main context never refreshes the main binding merely as part of retry or settlement. Loss can be detected by any tree reconciliation, including one triggered while resolving an unrelated explicit context; in that case the state changes silently and the next main-context operation raises. Unexpected disappearance is treated as lost evidence, not as an invitation to choose a replacement. `SetMainContextId` validates its argument against a fresh `browsingContext.getTree` and rejects both unknown IDs and child browsing contexts.

A deliberate close is different. When `ExecuteCloseContext` closes the currently pinned main context, the wrapper returns to the **unbound** state rather than the lost state, because the caller demonstrably knows the context is gone. This applies only when `browsingContext.close` returns a confirmed response. If the close outcome is ambiguous, the binding stays pinned; if the browser did close the context, the later `contextDestroyed` event moves it to **lost**, so the caller must pin explicitly. Ordinary automatic pinning then applies again on the next resolution: if exactly one top-level context survives, it is pinned without an explicit call; if several do, the caller must choose with `SetMainContextId`. `ExecuteCreateContext` and `ExecuteHandleUserPrompt` do not change the binding. A non-main explicit context is validated against `browsingContext.getTree` on first use and cached in `m_validatedContexts`; lifecycle loss, navigation, and destruction paths invalidate or reconcile that cache. An unknown or closed explicit context raises `ERR_ACTION_FAILED` instead of falling back to another tab.

## No Element Handle Class

SeleniumVBA itself exposes a `WebElement` class, but the BiDi wrapper deliberately has no equivalent. In this wrapper an element's identity is its **locator** (XPath, or an `Array` scope chain for Shadow DOM), not a held reference. Every action resolves the locator to a BiDi `sharedId` at the moment of use and consumes that `sharedId` within the same operation.

Three reasons converge on this design. First, a `sharedId` lives only as long as its document: v6.7 testing showed a captured reference still usable after 30 s on a live document, but rejected with `no such node` after document replacement and as Context Lost after the owning context was destroyed. SPA re-rendering (React, Wiz field-swapping) replaces nodes even without navigation. A handle class would therefore need to carry its locator to recover, at which point it is only a locator container. Second, it follows the stateless principle above: the caller holds no implicit state that the wrapper cannot see. Third, the stale-element retry in "Retry Decision Logic" is safe only because the wrapper owns resolution: it re-resolves from the locator before any page-visible effect. Visible-first selection is likewise evaluated on every resolution, so it always reflects the current page.

The costs are accepted. Repeated operations on the same element pay one `locateNodes` round trip each, which is local and usually small next to the post-action SPA wait. If the DOM changes, re-resolution may land on a different element of the same shape; write locators on stable attributes (`id`, `data-*`, `aria-label`) rather than positions. There is no element-relative search; express the relation in one XPath predicate (for example `//tr[td='foo']//button`) or, inside Shadow DOM, with an `Array` scope chain. The one held reference, the file-input `sharedId` captured by `input.fileDialogOpened` in `ExecuteSetFileSelectionViaDialog`, is consumed immediately by `input.setFiles` and does not outlive that operation. SeleniumVBA's classic `WebElement` objects remain available through the WebDriver session for code that wants them (`BiDi_Sample` Main02 counts results with `FindElements`); the wrapper does not wrap or track them.

## Explicit-Context Retry and Synchronization Isolation

The retry and synchronization paths follow the same ownership rule as ordinary command dispatch. On an action retry, `TryPreparePhase` refreshes the main-context binding only when the action target is the currently pinned main context. For an explicit non-main target, it removes only that context from `m_validatedContexts` and revalidates the same ID through `ResolveTargetContext`; it never chooses another top-level context as a substitute. If the explicit context has actually disappeared, the retry stops with `ERR_ACTION_FAILED` rather than drifting to a surviving tab.

`SettleAfterNavigation` and the URL-check branch of `SyncAfterAction` likewise call `UpdateMainContextId` only when the operation target is the pinned main context. An explicit iframe or non-main tab therefore remains usable even when the main binding is lost or when multiple top-level contexts exist and no main context has been pinned.

The same isolation now applies inside `ExecuteBiDiCommand` recovery. After a recoverable failure, the wrapper refreshes the main binding only when `allowContextRetarget=True`; an explicit-context command with `allowContextRetarget=False` keeps the same explicit target and never depends on main-context availability merely to continue its retry path. Deterministic pre-send rejections — 606, 607, and `WS_ERR_INVALID_UTF16` (9251) — do not enter recovery at all.

## Completion-Signal Context Ownership

The ordinary Arm APIs require no explicit context: an omitted `contextId` resolves to the current main browsing context. Advanced callers may arm a specific iframe or non-main tab by passing its context ID, but the arm, action, and consuming wait must remain aligned.

The first active arm owns the signal set. The `allowContextless` network opt-in does not change ownership: the arm still belongs to its resolved context, and only empty-context responses are additionally admitted. Cross-context attempts to add another arm, consume it through `WaitForNetworkIdleSpa`, or explicitly disarm it with a different context raise `ERR_ACTION_FAILED` rather than silently falling back to the main tab. This is an internal safety contract for ordinary calls and an explicit correctness contract for multi-tab automation.

The file-selection composite adopts an existing application-completion signal only after its target context has been resolved and ownership has been validated. A cross-context arm rejected at that boundary remains untouched. Failure cleanup disarms only when the composite actually adopted the signal set **and** an arm is still active; an ungated explicit-context run therefore does not resolve an empty context and send a stray disarm operation to the main context.

## Lifecycle-Loss Reconciliation

`ConnectTo` keeps `browsingContext.contextCreated` and `browsingContext.contextDestroyed` active as mandatory lifecycle subscriptions. The communicator classifies loss of those events, together with `navigationStarted`, into `LifecycleEventLossCount`; events whose top-level method cannot be recovered contribute through `UnknownCriticalEventLossCount`. v4.4’s wrapper also tracks corresponding dispatch-stage loss counters, so the lifecycle-relevant total used for reconciliation is the conservative sum of communicator and wrapper-dispatch evidence.

Before cached context state is trusted, the wrapper compares the current lifecycle-relevant loss total with its baseline. A change clears `m_validatedContexts` and marks the topology as needing reconciliation. The next context-sensitive operation refreshes `browsingContext.getTree`, rebuilds the cache, and verifies any pinned main context instead of assuming that a missed lifecycle event left the cache correct.

## Exclusive One-Shot Capture Ownership

v4.4 treats download-batch, new-top-level-context, file-dialog, and navigation HTTP-status capture as mutually exclusive composite transactions because all four use class-level one-shot state. `EnterExclusiveCaptureOperation` / `LeaveExclusiveCaptureOperation` reject a nested capture with `ERR_REENTRANT_CAPTURE` before the nested call can mutate shared state. This matters when `AllowUiPump=True` or an outer wait pumps Office messages and VBA can re-enter through an event or timer callback.

The guard is not intended to disable UI responsiveness. It fixes transaction ownership — one owner, one arm boundary, one cleanup path — while still allowing guarded yields. If a fatal reset becomes necessary during ownership, volatile reset work can be deferred until the owning transaction completes its cleanup.

## Exactly-One New Top-Level Context Capture

`ExecuteOpenNewContext` is the side-effect-safe helper for an XPath trigger expected to open one new tab or window. It resolves the trigger first, snapshot the current top-level context IDs, drain buffered events, arm a one-shot capture, and then perform one trusted BiDi pointer click. Only top-level `browsingContext.contextCreated` events absent from the baseline are candidates.

Correlation prefers `params.originalOpener == ownerContextId`. When `originalOpener` is absent, the pre-trigger baseline provides the fallback correlation mode (`baseline-diff`). After the first candidate, a short `NEW_CONTEXT_SETTLE_MS = 150` window detects a second candidate; multiple candidates, destruction of the captured context, or any lifecycle-relevant event loss after the arm boundary fail the operation rather than guessing. The trigger is never replayed automatically. The returned dictionary carries `context`, `url`, `originalOpener`, `clientWindow`, `ownerContext`, `ownerClientWindow`, `correlation`, `candidateCount`, `foreignIgnored`, and a derived `kind` of `tab`, `window`, or `unknown` when client-window evidence permits that distinction. v4.4 also records the capture lifecycle through `[NEW-CONTEXT-ARM]`, `[NEW-CONTEXT-CAPTURED]`, `[NEW-CONTEXT-SETTLED]`, and failure/ignored variants such as `[NEW-CONTEXT-AMBIGUOUS]`, `[NEW-CONTEXT-LOSS]`, and `[NEW-CONTEXT-TIMEOUT]` in the signal/Discovery timeline.

## Contexts Outside the BiDi Browsing-Context Tree

Not every page that classic WebDriver can switch to is a BiDi browsing context. On Edge 154 (observed 2026-10-03), the print preview opened by `window.print()` (`edge://print/`) appeared in CDP `Target.getTargets` as an attached `page` target and in classic WebDriver as a second window handle, but not in `browsingContext.getTree`. With no context ID, `script.callFunction` and `sharedId` cannot reach it, so `ExecuteFindWindowContextId(MatchByUrl, "edge://print")` times out by design and the wrapper does not attempt a CDP side path. Operate such pages through classic SeleniumVBA. This is an observed implementation difference, not a protocol rule; the classic route depends on how the driver enumerates CDP page targets.

## Realm ID Management and Caching

The `GetScriptRealmId` function implements a Dictionary cache keyed by contextId (`m_cachedRealmIds`), avoiding duplicate queries for the same context. It preferentially selects the “window”-type Realm, preventing erroneous connection to Service Workers or other Realm types.

## Safe Initialization in ClearState

`ClearState` refreshes volatile caches and per-context dictionaries without discarding unconfirmed server-side subscription ownership. Active subscription keys and retired server-issued subscription IDs are first released when possible; if the socket is already unavailable, v4.4 copies the issued IDs together with the BiDi session identity into a deferred-cleanup registry for same-session reconciliation. It also resets the CDP session id, main-context binding, resource-blocking token collection, completion-signal state, short-lived file-dialog capture, download capture, new-context capture, lifecycle-reconciliation baseline, and HUD fingerprint/retry state. There is no wrapper-side in-flight network dictionary to reset; consensus counters live in the browser probe.

The file-dialog reset here is deliberately local. It clears the VBA-side one-shot capture fields (`m_fileDlgArmed`, `m_fileDlgSeen`, owner context, captured `sharedId`, and `multiple` metadata), but it is not proof that Chromium’s `Page.setInterceptFileChooserDialog` state has been disabled. That interceptor is browser-side state and is tracked separately through `m_fileChooserInterceptMayBeActive`, its owning context, and its held CDP session so cleanup can survive ordinary wrapper-cache resets. The same distinction applies to browser-global download behavior: volatile download-capture fields are reset locally, while `browser.setDownloadBehavior` cleanup state is tracked separately across teardown paths.

## Chapter 6 — A Hybrid W3C BiDi / CDP Strategy for Browser-Side Control

The base design continues to speak W3C WebDriver BiDi for browser automation, while deliberately retaining narrowly scoped Chromium CDP tunneling where the browser itself can enforce a rule or suppress native UI more safely than a client-side workaround. There are two such uses: declarative resource blocking and temporary native file-chooser suppression. The latter does not replace the BiDi file-selection flow; it only prevents the operating-system picker from appearing while BiDi observes the chooser event and applies the file selection.

## The Deliberate Use of CDP (`Network.setBlockedURLs`) for Resource Blocking

Even after the WinSock migration, pure BiDi interception (`network.addIntercept`, `network.failRequest`) remains a poor fit for this VBA architecture. It requires the client to receive each intercepted request, decide, and send a reply back over the same automation channel. That makes high-volume network traffic part of the control loop itself.

The WinSock transport is non-blocking and more resilient, but avoiding unnecessary request-by-request round trips is still the stronger design. `ExecuteEnableResourceBlocking` therefore continues to drive CDP’s `Network.setBlockedURLs` through BiDi’s `goog:cdp.sendCommand` tunnel.

- **Silent blocking at the browser network layer:** Pattern matching and blocking are handled inside the browser. No interception decision messages have to be serviced by VBA.
- **Lower event-loop contention:** The WinSock pump removes the old blocking-receive failure mode, but resource blocking still stays out of the BiDi request/response path, reducing traffic and keeping synchronization polls cleaner.
- **Diagnostic visibility:** Blocked requests still appear as `network.fetchError`, allowing `[BLOCK]` discovery-log lines without turning blocking into a synchronous client decision.

The result is a hybrid model: standards-based BiDi remains the automation and event substrate, while CDP is reserved for narrowly scoped browser-side capabilities that do not yet have an equivalent practical BiDi operation.

## Narrow Chromium CDP Use for Native File-Chooser Suppression

A second, deliberately narrow CDP dependency handles the short-lived file-input case. Some applications create an `<input type="file">` only around the instant a trusted user gesture opens a chooser. Resolving that element by XPath before the click is therefore impossible, while allowing the operating-system picker to appear would block unattended automation.

`ExecuteSetFileSelectionViaDialog` solves that race as a composite operation. An application-completion signal is recommended once the site-specific evidence is known, but a missing arm is intentionally not an entry error. If a signal is already armed, it must belong to the same BiDi browsing context and it gates the final SPA wait. If no signal is armed, the operation continues as an ungated discovery run; with Discovery Log recording enabled, the resulting DOM/network timeline is the evidence used to choose the next run’s arm. An ungated STABLE result is therefore diagnostic rather than proof of application completion: idle-only consensus cannot distinguish “the application finished” from “the application ignored the change” when both end in quiescence.

1. Reuse any already armed application-completion signal (`ArmNetworkSignal`, `ArmContentSignal`, and/or `ArmVisibilitySignal`) and validate that its owner is the same BiDi browsing context. If no signal is armed, continue in ungated discovery mode.
2. Subscribe to `input.fileDialogOpened` before enabling interception and before clicking.
3. Resolve the trigger element before the local file-dialog arm is raised.
4. Obtain a **fresh** CDP session from `goog:cdp.getSession` for the same target context. The general main-context CDP cache is not trusted for this step because an OOPIF, popup, or externally navigated context may have a different or stale session.
5. Enable Chromium `Page.setInterceptFileChooserDialog` with `enabled=true` and `cancel=false`. The wrapper marks the interceptor as *may be active before sending the state-changing CDP command*, so lost replies cannot erase the need for later cleanup.
6. Drain buffered asynchronous events through `ProcessRecorderQueue` while the local file-dialog arm is still down, then snapshot the file-dialog-relevant loss total (`FileDialogEventLossCount + UnknownCriticalEventLossCount`). This catches events preserved during the CDP round-trips before they can be mistaken for the new operation; the drain remains best-effort rather than a formal queue watermark.
7. Arm the one-shot file-dialog capture and trigger the chooser through trusted BiDi `input.performActions`.
8. Accept only an `input.fileDialogOpened` event whose `params.context` equals the operation’s owner context. The event must expose the `multiple` field and an HTML file-input `element.sharedId`; elementless picker paths are outside this API contract.
9. Call BiDi `input.setFiles` on that captured `sharedId`. If more than one path was supplied, the event must report `multiple=true`.
10. Clear the local capture, explicitly disable the native-picker interceptor, and only then run the final SPA synchronization — signal-gated when an arm exists, idle-only when it does not. Operation cleanup also disarms any application-completion signal owned by this file-selection composite, including failure paths that exit before the trusted chooser-trigger click or before the final SPA wait begins.

After the local arm is raised, the wrapper continuously checks the relevant-loss delta. If it becomes nonzero, capture stops immediately with `ERR_BIDI_PROTOCOL` and `AsyncEventsDroppedSinceArm=<n>` because exact observation is no longer trustworthy. If the loss delta remains zero but no matching chooser event arrives before `fileDialogTimeoutMs`, the method raises the ordinary `FileDialogTimeout`.

The use of `cancel=false` is intentional: it is the verified coexistence mode that suppresses the native picker UI without synthesizing a site-visible cancel. The CDP role ends at the native-UI boundary. Chooser observation, element identity, file selection, trusted pointer input, and final synchronization remain BiDi-driven.

The evidence for this interception path is kept in three layers. **The protocol contract** is limited to native-chooser interception: Chromium does not show the native picker and transfers control to protocol clients while interception is enabled. **Project probe evidence** goes further for the tested Edge/Chromium environment: a captured file-input reference remained usable by `input.setFiles` after the page removed the input and a 10-second delay elapsed. That result supports the practical resilience of the hand-off at the tested time scale, but it is empirical rather than a WebDriver BiDi or CDP lifetime guarantee. **Still unverified** are any absolute retention deadline and behavior across navigation, tab destruction, or equivalent context replacement.

The cleanup contract is conservative because the interceptor lives in Chromium rather than in VBA. If the originally held CDP session can no longer disable it, cleanup may resolve a fresh session for the same context and try again. A new `ConnectTo` also performs a best-effort sweep across current Chromium browsing contexts to disable residual interception left by an earlier VBA project termination; implementations without `goog:cdp` are left untouched. `Shutdown` makes the same release attempt before CDP detach or transport teardown.

This second CDP use is therefore materially different from resource blocking. Resource blocking installs a browser-side declarative network rule for efficiency; file-chooser interception temporarily suppresses native UI so that a standards-based BiDi event-and-command sequence can complete without an operating-system dialog.

## Browser-Global Download Behavior Through WebDriver BiDi

Download policy is controlled through the standard BiDi `browser.setDownloadBehavior` command rather than through CDP. `SetDownloadFolder` installs an `allowed` behavior with a resolved existing destination folder, `SetDownloadDenied` installs `denied`, and `ClearDownloadBehavior` sends `downloadBehavior: null` to restore browser/default policy. The current helper intentionally uses global scope and does not expose `userContexts` because that scope is outside the measured download evidence set.

The wrapper marks download behavior as potentially changed **before** dispatching the state-changing command. A confirmed response clears the unknown-state flag; an ambiguous outcome leaves `m_downloadBehaviorStateUnknown = True`, and the download engine used by `ExecuteDownloads` refuses to start another batch until an explicit `SetDownloadFolder`, `SetDownloadDenied`, or `ClearDownloadBehavior` succeeds. `ConnectTo` performs one best-effort residual clear for a browser session that may have survived an earlier VBA project termination. Unsupported implementations (`unknown command` / `unsupported operation`) are accepted as not providing this capability rather than making the whole BiDi connection fail.

## A Standards Request: Declarative Resource Blocking in WebDriver BiDi

As checked against the [WebDriver BiDi Editor’s Draft](https://w3c.github.io/webdriver-bidi/) on July 26, 2026, the network model defines `network.addIntercept`, URL-pattern filtering, and `network.failRequest`, but still does not define a command equivalent to CDP’s `Network.setBlockedURLs`: a rule registered once and then enforced entirely by the browser.

For requests that require a dynamic decision, modification, authentication response, or synthetic response body, interception is the correct abstraction. Static resource blocking is different. When the intended decision is simply “always block requests matching these patterns,” pausing every matching request, delivering an event to the client, waiting for a client command, and then resuming the browser adds a control-channel round trip without adding any useful decision-making capability.

I would therefore like to request a declarative resource-blocking command in WebDriver BiDi. The command name and schema below are illustrative rather than a specification proposal:

```
{
  "method": "network.setBlockedUrlPatterns",
  "params": {
    "urlPatterns": [
      {
        "type": "pattern",
        "hostname": "doubleclick.net"
      }
    ],
    "contexts": ["<optional browsing context>"],
    "userContexts": ["<optional user context>"]
  }
}
```

The intended behavior would be straightforward:

- Register or replace a set of URL patterns once, rather than intercepting each request individually.
- Evaluate those patterns inside the browser’s network layer before the request is dispatched.
- Block matching requests without requiring a per-request BiDi event/command round trip.
- Allow session-wide, browsing-context, or user-context scoping where the browser can support it consistently.
- Continue to emit an observable event such as `network.fetchError`, with a recognizable blocked-by-client reason, so logging and diagnostics are not lost.
- Provide an explicit way to clear or remove the registered rules.

This would complement, not replace, `network.addIntercept`. Interception should remain available for cases where the client genuinely needs to inspect or alter each request. Declarative blocking would cover the narrower and common case in which the decision is fixed in advance.

The motivation is not limited to VBA. Per-request interception is costly for remote clients, high-volume pages, embedded runtimes, and synchronous or single-threaded language bindings. In Playwright’s WebDriver BiDi adoption issue, [the project describes interception as “prohibitively expensive and therefore impractical”](https://github.com/microsoft/playwright/issues/32577) for a persistent emulation use case. The same cost pattern applies when a client must repeatedly adjudicate requests that it already knows it will reject.

The proposal also fits patterns already present in WebDriver BiDi. The specification includes persistent declarative configuration through `network.setCacheBehavior` and `network.setExtraHeaders`, while `network.addIntercept` already provides browser-side URL-pattern matching. A declarative block list would therefore reuse existing concepts rather than require a new interception architecture.

This is not a claim that such a command is already planned. Cross-browser semantics would still need to be defined, including redirect handling, Service Workers, WebSocket and WebTransport coverage, interaction with ordinary intercepts, multi-session precedence, and the exact error event exposed for a blocked request. Nevertheless, the current CDP dependency demonstrates a concrete interoperability gap and a practical use case for standardization.

Until WebDriver BiDi provides such a browser-enforced rule, this project will continue using the CDP tunnel for resource blocking. The preferred long-term outcome, however, is clear: the same declarative capability should become available as a browser-neutral WebDriver BiDi command.

## Anti-RAT & Loopback Restriction

The WinSock transport is intentionally not a general-purpose remote WebSocket client. It accepts only local `ws://` BiDi endpoints using `localhost`, `127.0.0.1`, or `[::1]`, with an optional port and a path boundary. `AttemptAutoConnect` also requires a `/session` URL issued by the driver. This keeps the channel in the local IPC category and prevents accidental or malicious use as an outbound WebSocket bridge.

## SendMessage’s Retransmission Ban

`SendMessage` may attempt to heal the socket after a failure, but it never replays the same JSON payload. A send failure can be ambiguous: the browser driver may already have accepted the request ID. Any safe retry must be an upper-layer decision that creates a new ID, and the wrapper disables such retries for state-changing operations on ambiguous outcomes.

One send failure is exempt from that ambiguity. When the codec rejects invalid UTF-16 in caller-supplied text, the rejection happens before a frame exists, so the driver cannot have seen the request. `SendMessage` raises `WS_ERR_INVALID_UTF16` for this case instead of returning `False`, and the transport stays open. The caller may correct its input and issue a new command without any of the reasoning that ambiguous outcomes normally require.

## Strategic Error Buffer

`On Error Resume Next` remains limited to local, captured, or best-effort scopes. The transport no longer relies on WinHTTP-specific recovery paths, but timing races still exist at the protocol level: contexts can disappear, probes can be lost, and browser-side events can arrive while the wrapper is updating state. The rule is unchanged: transient inconsistencies may be tolerated only where the primary action result cannot be hidden.

## Chapter 7 — Robustness and AI Integration

High-purity log generation and debugging features designed for next-generation automation.

## Four-Layer JSON Traversal Engine

Access to deep data hierarchies is achieved with JS-style path notation (e.g., `"result.contexts.0.url"`). A four-layer architecture guarantees safe access while avoiding the instability of VBA’s ByRef return values:

- **Layer 0 (Shield):** The `Assign` helper — selects `Set` or `Let` according to `IsObject`, avoiding duplicated object/scalar assignment branches. It is not a blanket error suppressor.
- **Layer 1 (Physical Search):** `InternalTraverseFromObject` — iterative traversal of Dictionaries and Collections using dot-separated path segments.
- **Layer 2 (Gatekeeper):** `GetPathValue` — performs type arbitration and safely returns the Layer 1 result as a Variant.
- **Layer 3 (Exit Accessors):** `GetPathString`, `GetPathObject`, `GetCleanResult` — purpose-specific, type-converted accessors.

## AI-Ready Discovery Recorder

When recording communication and rendering events, URL and MIME filters remove high-volume noise while retaining suppressed-event counts. `excludeImagesAndCss` (default True) suppresses images, stylesheets, and fonts; `excludeScripts` (default True) suppresses script loads, identified by a URL path ending in `.js` or `.mjs` after query and fragment removal, so `.json` is never matched. Script loads are `<script>` resource loads, not Fetch/XHR, and never drive consensus; on Outlook on the web they were about 64% of an unfiltered log (1,500 of 2,300 lines). Suppression applies to the timeline only: `[REQ]`, `[RES]`, and `[ERR]` for the same request are suppressed together, the events are still parsed and dispatched (signals, request-hop tracking, and BODY candidates are unaffected), and they are counted in `[SUPPRESSED]`. Extensionless script URLs remain visible. `StartDiscoveryLog` stages its new collections, timestamp, options, carryover state, subscription state, and optional WebDriver BiDi network data collectors before publishing the new recorder state. Response-body capture remains enabled by default (`captureResponseBodies=True`) while request-body capture remains opt-in (`captureRequestBodies=False`). Collector setup is capability-probed and a collector failure does not disable the ordinary Discovery recorder. A failed new start leaves recording disabled; a failed restart preserves the previous recorder and its existing logs.

In v5.3, Discovery recording requires the exact GLOBAL `network.responseCompleted` subscription to remain available continuously. If the global subscription already exists, `StartDiscoveryLog` reuses it; otherwise it creates one through the wrapper-wide active-subscription registry. The Recorder no longer keeps a separate ownership ID for this event. A context-scoped `network.responseCompleted|<ctx>` subscription is not sufficient for Discovery coverage, and failure to establish the global subscription aborts the new recorder start transactionally. Cleanup is handled by the wrapper-wide subscription registry.

`StopAndSaveDiscoveryLog` drains the queue while `m_isRecording` is still True and emits the final `[REQ-UNPAIRED]` request-hop summary before recording is disabled. It then sets recording False before any synchronous `network.getData` body pulls. This keeps body retrieval outside recorder dispatch and SPA-wait timing. The suppression summary is appended afterward and the file is written as plain UTF-8 without a BOM. Most event and signal lines are routed through `PushTimelineLine`, which maintains a 5,000-entry ring-buffered path and records evictions for a `TRUNCATED` header. SPA-wait diagnostics, including `[SPA-WAIT-BEGIN]` and `[SPA-WAIT-END]`, also use `PushTimelineLine`. The final `[SUPPRESSED-TOTAL]` / `[SUPPRESSED]` summary is appended directly to `m_recorderLogs` after the ring-buffered timeline, and BODY STORE is written separately from that timeline. Accordingly, 5,000 is not a strict cap on the whole file, and BODY STORE diagnostics can still be written even when no ordinary timeline entry survives.

A save failure is terminal for the current recording. `StopAndSaveDiscoveryLog` preserves the primary error (for example `ADODB.Stream` 3004 for a locked output file), leaves VBA's active handler with `Resume`, closes any open stream, releases body collectors, and resets recorder, BODY, and request-hop state on a best-effort basis before re-raising that original error. The unsaved timeline and BODY STORE are discarded and cannot be recovered by calling Stop again; a second call produces no saved output, although it still drains the event queue and retries body-collector release on a best-effort basis. Callers should ensure the output path is writable before stopping, and must start a new recording after a failed save.


v5.3 removes the navigation-time Recorder pause optimization. While Discovery recording is active, GLOBAL `network.responseCompleted` remains subscribed through URL/readyState stability and SPA settlement, so the Recorder no longer intentionally creates response-observation gaps in order to reduce event traffic. The legacy `[REC-PAUSE]`, `[REC-RESUME]`, `[REC-RESUME-FAIL]`, `[REC-PAUSE-OPEN]`, and `[REC-PAUSE-SKIP]` diagnostics are therefore no longer part of the current logging contract.

The recorder also tracks request hops by `(requestId, redirectCount)`. In v5.3, `[REQ-UNPAIRED]` reports the exclusive `open-at-end` and `other` categories. `open-at-end` means the hop still had no observed terminal event or redirect advance when recording ended; `other` means no terminal event was observed even though later evidence showed the hop was no longer open. The former `pause-exposed` category is removed because the Recorder no longer creates deliberate `responseCompleted` observation gaps. The core invariant remains unchanged: diagnostics must not change the synchronization behavior being diagnosed.

Probe, completion-gate, file-dialog, new-context, and download diagnostics participate in the same timeline. `[SPA-FILTER-INVALID]` identifies an invalid CSS ignore selector once per session, while `[SPA-SIGNAL-CTX-MISS]` records the first matching network response rejected because it came from the wrong or empty context. `[SPA-SIGNAL-CARRYOVER]` and `[SPA-SIGNAL-CARRYOVER-HIT]` record completion arms that survived into a composite operation and whether they were hit during it. The short-lived file-selection path adds `[FILE-DIALOG-ARM]`, `[FILE-DIALOG-HIT]`, `[FILE-DIALOG-CTX-MISS]`, and bounded ignored-event evidence. New-context capture adds the `[NEW-CONTEXT-*]` lifecycle described in Chapter 5. The v4.4 download batch path emits raw `[DOWNLOAD-WILL-BEGIN]` / `[DOWNLOAD-END]` observations plus batch records such as `[DOWNLOAD-BATCH-ARM]`, `[DOWNLOAD-BATCH-START-ACCEPTED]`, `[DOWNLOAD-BATCH-END-MATCHED]`, context/ignored variants, and `[DOWNLOAD-BATCH-FILENAME-COLLISION]`. A start that never reaches `[DOWNLOAD-BATCH-START-ACCEPTED]` is therefore distinguishable from a transfer that started but never reached a matched terminal event.

For the short-lived file-input path, this recorder is part of the control strategy rather than merely a post-mortem aid. Absence of a completion arm is deliberately non-fatal: the first run may use ungated idle-only synchronization so the log can reveal the post-`input.setFiles` mutation paths and relevant network responses. Those observations then drive `ArmContentSignal`, `ArmVisibilitySignal`, and/or `ArmNetworkSignal` on the next run, where the timing can be measured under an explicit gate. Turning “no arm” into an immediate error would stop the operation before those observations exist and would break the project’s log-driven **observe → arm → re-measure** improvement cycle.

## Discovery Network-Key Normalization (introduced in v5.2)

Discovery timeline network keys are intentionally structural rather than raw URLs. `[REQ]`, `[RES]`, `[ERR]`, and `[BLOCK]` remove the URL fragment, redact matrix/path assignment values such as `;ord=123` to `;ord=`, and preserve query-parameter names while stripping their values. Two parameters are deliberate exceptions. `rpcids` keeps its value because it identifies the RPC family. Since v6.2, `action` keeps its value when that value is 1 to 64 characters of letters, digits, `_`, `.`, or `-`, because on multiplexed endpoints it names the operation rather than user data (Outlook's `service.svc` serves `UpdateItem`, `GetDlpPolicyTips`, `FindItem`, and dozens of others under one path); any other `action` value is stripped as before. Before this change an armed save response and an unrelated background check produced the identical key `service.svc?action=&app=&n=`, so a `[SPA-CONSENSUS-SUSPECT]` firstJson could not be classified without reading BODY STORE. Navigation detail replaces the fragment with `#<fragment-redacted>` (a bare trailing `#` stays `#`). Navigation fragments are treated as potentially sensitive and are redacted as a whole in Discovery Log output: OAuth/OIDC responses can place an authorization code, tokens, or state there, and the wrapper does not attempt to classify individual fragment keys such as `code`, `token`, or `state`. Only a literal `#` delimits the fragment; an encoded `%23` is ordinary URL text. The redaction affects log output only, never the URL used for navigation or matching. It was introduced after an Outlook on the web log was found to contain a live-format authorization code in a `[NAV]` line.

Since v6.2, `[REQ]`, `[RES]`, `[ERR]`, and `[BLOCK]` also mark events outside the recorder's top-level browsing context. `ctx=(empty)` means the event has no browsing context, typically a Web Worker request: Fetch/XHR consensus cannot see it and it never enters a wait's render-evidence set. `ctx=other:<first 8 characters>` means another tab or frame. Lines in the recorder context carry no `ctx=` field. The reference context is resolved once at `StartDiscoveryLog` (the BODY collector context when one exists, otherwise the main context) and is shown in the header as `CONFIG ... recorderCtx=`; if it cannot be resolved, `recorderCtx=unresolved` is written and only empty contexts are marked. `[SPA-ACT]` lines end with `n=<entries listed in this sample>` and, when the probe's list overflowed, `dropped=<entries not listed>`; the listing itself is still cut at 500 characters.

`[SUPPRESSED]` uses a deliberately coarser identity because it is a noise-frequency summary, not a full endpoint-shape log. It aggregates by normalized host+path and retains only the presence of `?`; query parameter names and values are omitted. BODY capture uses a third identity internally: `method + fragment-free full URL + MIME`. Query values therefore remain private in the saved log but still distinguish BODY capture identities internally, so different query values can each consume their own BODY slot while repeated requests to the exact same URL share the per-identity cap.

## Selective Network Body Capture (introduced in v4.8)

v4.8 introduced selectively retained network payloads through the standard WebDriver BiDi `network.addDataCollector` and `network.getData` commands; the current version retains that architecture, including the scope, identity, and AI-facing representation refinements introduced through v5.2. Response and request bodies use separate collectors scoped to the resolved top-level browsing context. Response capture is the default because it materially improves API-level analysis while avoiding the higher exposure risk of request payloads:

```
' Defaults
bidi.StartDiscoveryLog _
    captureResponseBodies:=True, _
    captureRequestBodies:=False
```

The body path is deliberately narrower than the ordinary network recorder. Only JSON / JSON-like MIME types become body candidates. With no explicit body pattern, v5.3 requires **both** the recorder’s top-level browsing context and `Sec-Fetch-Site` of `same-origin`, `same-site`, or `none` (since v6.2 the header is read from the raw event text when that is unambiguous, with the parsed-object lookup as fallback; the rule is unchanged); child-context, cross-site, and unknown-site/context candidates are deliberately not pulled into the saved log. The `[BODY-SKIP] reason=child-context` label is emitted for any event context other than the recorder's top-level context, including a separate top-level tab, not only for child frames. `AddBodyCapturePattern` changes this into an explicit allow-list: matching patterns may intentionally bypass those default log-side scope checks, while actual `network.getData` availability still depends on what the browser-side collector retained.

Body patterns match the public normalized endpoint key (which since v6.2 includes identifier-shaped `action` values), but the per-body cap does not use that redacted key. The internal identity is `method + fragment-free full URL + MIME`, so query values remain private yet different query values count as distinct capture identities; repeated requests to the exact same URL share the cap. The event handlers never call `network.getData`; they retain candidate metadata and the full internal request ID only. One candidate per internal identity is kept (first arrival); beyond that the per-identity limit still reports `reason=cap`.

Bodies are chosen at Stop rather than on arrival. Up to 1,000 metadata-only candidates per data type are retained (`reason=index-cap` beyond that), each with its socket arrival time and whether it matched an explicit body pattern. At Stop, at most 25 bodies per data type are pulled in this priority order, newest first within a priority:

1. `evidence:suspect` / `evidence:unresolved` — the response was judged SUSPECT or UNRESOLVED by a wait's render-evidence verdict (only waits that reached STABLE produce verdicts);
2. `pattern` — the response matched `AddBodyCapturePattern`;
3. `wait` — it arrived during a recorded SPA wait or within 1.5 s before one began;
4. `other`.

Selected bodies are written in arrival order with `priority=` and `at=` on each `[BODY]` / `[BODY-MISS]` line; unselected candidates are summarized as `[BODY-SKIP] reason=unselected`. First-arrival capping was replaced because long application boot sequences filled every slot before any user action occurred: on Outlook on the web all 25 slots were taken by boot-time configuration responses before the compose screen opened, while the SUSPECT responses that most needed inspection were discarded. With Stop-time selection the same flow yielded 3 `evidence:suspect`, 12 `wait`, and 10 `other` bodies, 83 unselected boot-time candidates, and `miss=0`.

Stop-time selection depends on the browser-side collector still holding the data at Stop. This was measured rather than assumed. In two Outlook on the web runs of about 30–40 seconds, every candidate from the recorder's top-level context was retrievable at Stop (114/114 and 113/113), including responses that arrived during application boot, so no eviction was observed for the pulled candidates. That result covers the retrieved JSON candidates at that load and duration; it is not a retention guarantee for heavier pages or longer runs, and the retention of non-JSON data was not examined. The same measurement showed that a collector scoped to the top-level context does not collect empty-context (Web Worker) responses: all 39 were reported by `network.getData` as never collected (`didn't collect response data`), not evicted. A collector created without `contexts` collected all of them (39/39, 152/152 overall, `miss=0`). The default remains the top-context collector; a session-wide collector would also retain other tabs' data and cannot attribute worker traffic, so it is a candidate opt-in rather than a default.

The browser-side collector uses `maxEncodedDataSize = 262144` (256 KiB) as a per-item retention eligibility limit. The current file-side AI guard remains **8,192 characters per body after normalization/compaction**, not the earlier 32,768-character limit. These are different controls: the collector limit decides whether a payload can be retained by the browser, while the file-side limit bounds what is written to BODY STORE. When an event reports a numeric `bodySize` larger than the collector limit, the wrapper emits `[BODY-SKIP] reason=oversize` without calling `network.getData`. Because BiDi permits `bodySize` to be null, an unknown-size item may instead reach Stop and later produce `[BODY-MISS]` if the collector did not retain it.

Before the final 8 KiB guard is applied, parseable JSON is prepared for AI-oriented logging. XSSI/length-framed JSON is normalized into a canonical frame envelope, and JSON strings embedded inside JSON may be expanded structurally. Payloads at or below 4,096 source characters are kept lossless with respect to content sampling: ordinary small JSON remains as retrieved, while small framed JSON may be normalized without lossy array/object sampling. Larger parseable payloads use bounded structural compaction (normal pass: strings 256 chars, arrays 3 items, objects 24 members; strict retry: 128/2/10) before final prefix truncation is considered. `[BODY]` therefore reports `sourceChars`, `loggedChars`, `normalized=`, `compacted=`, and `truncated=` so a consumer can distinguish canonicalization, lossy structural reduction, and final truncation.

BODY STORE is written after the ordinary timeline and is independent of the 5,000-entry timeline ring. `[BODY] RESPONSE` and `[BODY] REQUEST` records carry the same ShortId + **public normalized key** used by `[RES]` / `[REQ]`, allowing direct correlation without exposing the internal full-URL capture identity. `[BODY-SKIP]` records deliberate no-pull outcomes such as redirect, oversize, scope/pattern rejection, per-identity or candidate-index cap, or `unselected` at Stop; `[BODY-MISS]` means a selected `network.getData` retrieval failed and must not be interpreted as an empty HTTP body. `[BODY-STATS]` summarizes captured request/response bodies, normalized/compacted/truncated counts, source/logged/saved characters, miss/unavailable outcomes, and skip categories including `skipUnselected`.

Body retrieval is intentionally deferred until `StopAndSaveDiscoveryLog`. No `network.getData` round-trip is issued from `FormatAndStoreLog`, `ProcessRecorderQueue`, or an active SPA wait. This protects `m_isProcessingQueue`, DOM-quiet measurement, completion-signal timing, and the polling-side confirmation window from recorder-induced synchronous work. Collector cleanup is best-effort at Stop and is also attempted during Shutdown while the BiDi session is still reachable.

Request and response bodies may contain credentials, authentication material, personal information, or other confidential data. Request capture therefore remains explicitly opt-in. The current default retrieval/logging scope remains intentionally conservative, but the browser-side BiDi collector may still temporarily retain other data until cleanup, and explicit `AddBodyCapturePattern` entries intentionally broaden the log-side allow-list for matching keys. Any Discovery Log containing BODY STORE should therefore be reviewed before it is shared with an AI system or a public forum.

## ProcessRecorderQueue — Circuit Breaker and Fairness-Bounded Drains

The `ProcessRecorderQueue` function implements layered defenses:

- **Re-entrancy prevention:** `m_isProcessingQueue` excludes nested drains.
- **No synchronous body pull inside dispatch:** request/response body candidates are recorded during event handling, but `network.getData` is deferred to `StopAndSaveDiscoveryLog` after recording is disabled. The queue drain therefore never turns a recorder event into a nested protocol round-trip.
- **Three-state retrieval:** `TryGetParsedEvent` distinguishes an empty queue from a consumed valid event and a consumed rejected event.
- **Continuation after bad input:** oversized, malformed, or filtered events count toward the 1,000-message batch ceiling but do not stop later events in the same batch from being dispatched.
- **Fairness-bounded internal drains (v4.6):** opportunistic non-blocking drains stop after at most 32 consumed messages or about 250 ms of queue work. Remaining FIFO entries are preserved for the next drain instead of letting one event burst monopolize the VBA execution thread.
- **Bounded diagnostics:** the first five drop reasons in a batch may be printed under debug mode; additional drops are summarized.
- **Circuit breaker:** ten consecutive dispatch errors abandon the batch rather than hanging the host.
- **Lock guarantee:** the processing flag is released through the common cleanup path.

The 32-message / 250-ms limit applies only to the internal non-blocking drain path used by context resolution, URL-stability heartbeat work, and SPA-wait startup. Explicit `ProcessRecorderQueue` calls retain the normal 1,000-message batch contract, so operations that intentionally flush recorder work keep their previous semantics.

## Recorder Throughput and Observation Semantics (v6.2)

**Principle.** Recorder optimization must not change observation semantics. Raw-event shortcuts and reduced parse copies are used only when equivalence with the full-parse path can be established; otherwise processing falls back to the original full-parse path.

**Why this was needed.** The Recorder parses and dispatches every subscribed event on the single VBA thread, inside the same drains that waits and element searches perform. On Outlook on the web, a run with recording on took about twice as long as the same run with recording off (22.1 s vs 43.0 s on average). Arrival-to-dispatch lag reached about 13 s during application boot, probe samples became seconds apart, and waits and element searches ran against a different timeline from the unrecorded run. Several earlier observations (long boot, multi-second probe initialization, waits exceeding their budget) turned out to be largely Recorder load. The diagnostic was changing the behavior it diagnosed.

**Measured cost structure.** About 2,100 events per run, of which about 1,500 were script loads. Parse cost was roughly proportional to event size; request and response events averaged 12–16 K characters, and 73% of those characters were `params.request.headers`, `params.request.cookies`, and `params.response.headers`, with `responseCompleted` repeating the request's headers and cookies. Most dispatch time was not endpoint normalization but the BODY scope check reading `Sec-Fetch-Site` through the parsed header objects (about 35 ms per checked response).

**Script fast path.** While recording with `excludeScripts=True`, a `network.beforeRequestSent` / `responseCompleted` / `fetchError` event is handled without a JSON parse only when all of the following are read unambiguously from the raw text: `params.navigation` is null (a subresource, never a top-level navigation), `redirectCount` and `request.request` are present, the URL is a script by path extension (`response.url` for `responseCompleted`, `request.url` otherwise), a `responseCompleted` has a readable non-JSON `mimeType`, request-body capture is off for `beforeRequestSent`, debug mode is off for `fetchError`, and no armed network signal pattern matches the URL. Such an event goes through the same request-hop, request-cache, and `[SUPPRESSED]` code the parsed path uses, so `[REQ-UNPAIRED]` and suppression totals keep their meaning. Anything unproven is parsed normally.

**Raw `Sec-Fetch-Site`.** The BODY scope rule is unchanged; only the header source changed. The raw reader walks `params.request.headers[]` and returns FOUND (first case-insensitive match with an unescaped string value), ABSENT (the whole array was read and the header is not there), or UNCERTAIN. Only FOUND is used directly; ABSENT and UNCERTAIN fall back to the parsed lookup. The raw text is passed down the dispatch path as an argument, never kept in class state.

**Reduced parse copy.** For recorded network events, the parser receives a copy in which the contents of `params.request.cookies` and `params.response.headers` are removed (`[]` is kept), and `params.request.headers` too when request-body capture is off and the raw `Sec-Fetch-Site` state is FOUND or ABSENT. No current Wrapper consumer reads cookies or response headers; a future feature that does must update these preservation rules first. Dispatch still receives the original raw text. The copy is parsed without loss accounting; if that parse fails, the original text is parsed through `ParseEventText`, so a wrapper-built copy can never be recorded as a malformed received event (`fallbackOriginalParse`, expected 0).

**Measured effect (same Outlook on the web flow, recording on minus recording off).**

| Stage | Added run time |
|---|---|
| Before optimization | about +20.9 s |
| Script fast path | about +14.3 s |
| Raw `Sec-Fetch-Site` | about +8.4 s |
| Reduced parse copy | about +4.6 s |

These are measurements of one flow on one machine, not guarantees; event counts and machine load varied between runs, and one run showed every timing roughly doubled. In the last configuration, 1,264 of 1,734 events used the fast path, 444 network events were parsed from reduced copies (71.7% of parsed characters removed, no fallback), per-event parse time for request/response events fell by about 70–75%, maximum dispatch lag was about 4.7 s, and no events were lost. The event FIFO still reached about 1,000 of its 2,000-entry limit during boot bursts; the limit was deliberately not raised, because a larger buffer would not reduce lag or run time.

The staged figures above were taken while the mechanisms were being developed. One later confirmation pair, taken on the final implementation of these three mechanisms before this release's diagnostic additions, measured 18.17 s with recording off and 22.48 s with recording on (Stop and save 0.29 s), with `maxEventFifoDepth=1093`, `maxDispatchLagMs=3873`, and `asyncLossSinceStart=0`.

**Health line.** Every Discovery Log ends with `[RECORDER-QUEUE-STATS]`: `events` (taken from the event FIFO while recording), `parsed` (JSON-parsed), `fastPath` (handled without a parse), `reducedEvents` (parsed from a reduced copy), `fallbackOriginalParse` (reduced copy rejected and the original parsed instead; expected 0), `drains`, `maxEventFifoDepth` (sampled at the start of each recorder drain), `maxDispatchLagMs` with `maxLagArrivalAt`, `lagOver1s` / `lagOver5s`, `maxDrainGapMs` with `maxDrainGapEndAt`, `parseMs` / `avgParseUs` and `fastPathMs` / `avgFastPathUs` (parse or fast-path work only; event retrieval is excluded), and `asyncLossSinceStart`. Since v6.8, a nonzero loss carries its transport-cap share in parentheses, `asyncLossSinceStart=<n> (transportOversize=<m>)`: `m` events were dropped at the 5 MiB receive cap (`MaxIncomingSize`), never reached the timeline, and are absent from `[REQ-UNPAIRED]`. The value is the change of the communicator's existing `TransportOversizedEventCount` since `StartDiscoveryLog`; each such event is already counted once in the total. The header LEGEND defines each field for an AI reader. The line costs only counter updates and exists so that a site where the Recorder becomes expensive can be diagnosed without a special build. Fine-grained internal timing is deliberately not part of the release build. A per-method dispatch breakdown (`[RECORDER-DISPATCH-STATS]`) and per-block profiling were used during development, but builds carrying that instrumentation were flagged by antivirus scanners as false positives, so the release keeps only the coarse counters above. Future diagnostics should follow the same rule: prefer a few counters and summary lines over per-call timing, and re-scan the module after any change to the Recorder.

## Event JSON Parser (v6.8)

**Why.** After the v6.2 shortcuts, parsing was still the largest share of Recorder work. `WebJsonConverter.ParseJson` reads one character at a time with `Mid$` and appends each string character through a `Variant` buffer helper, checks for spaces several times per value, and runs three `Replace` passes over the whole message. `WebJsonConverter` belongs to SeleniumVBA, which this extension does not modify, so the faster parser lives in the communicator.

**Design.** `ParseJsonText` keeps the control flow and the result objects of `WebJsonConverter.ParseJson`: the same `Scripting.Dictionary` / `Collection` nesting, the same handling of duplicate keys, `\n` as `vbNewLine`, `\uXXXX`, single-quoted strings, the `<` case, large-number strings, and the `OptionsUseDoubleForLargeNumbers` / `OptionsAllowUnquotedKeys` settings read from `WebJsonConverter`. Only character access changed: characters are read from a byte view of the string, a string without escapes is copied with one `Mid$`, a number is copied as one slice, and the CR/LF/TAB removal runs only when those characters are present. When the parser rejects an input it calls `WebJsonConverter.ParseJson` on the same text, so a malformed event produces the same error number and the same loss accounting as before. The code carries an attribution comment for VBA-JSON (MIT, Tim Hall) and vba-json (BSD, Ryo Yokoyama); the full license texts are in `WebJsonConverter`.

**Escapes stay linear.** A string with escapes is processed segment by segment. The closing-quote position is searched again only when an escape consumed it, and the next backslash position is cached for the whole parse (`JpNextBackslash`); the read position only moves forward, so scanning is linear in the message length. An earlier development build searched again and copied the rest of the string at every escape, which made escape-dense strings quadratic; an external review found it before release.

**Measured.** Same 416 raw ServiceNow events (3.26 M characters, about 6,000 backslashes), five passes after a warm-up, in one session:

| Parser | ms per pass | µs per event | Ratio |
|---|---|---|---|
| `WebJsonConverter.ParseJson` | 1,001.7 | 2,408 | 1.00 |
| `ParseJsonText` | 278.3 | 669 | 0.28 |

All 416 results matched recursively, including key order and `VarType`. With escape-dense strings (one escape every three to four characters; `\n`, `\"`, `\\`, `あ`; 5,000, 10,000, and 20,000 escapes) the time roughly doubled with the count, and all twelve cases matched; in this extreme density `ParseJsonText` was up to about twice as slow as `WebJsonConverter` in the twelve measured cases, because each escape costs several calls. Real event streams are far sparser, which is where the overall gain comes from. On Main07 (Edge) the per-event Recorder parse time fell from 3,486 µs (v6.7) to 1,286 µs on the release build. The peak FIFO depth did not change, because it is set by events that arrive while `browsingContext.navigate` is waiting for `interactive` (Chapter 16); in two runs per parser on a development build, the backlog cleared about 6 s after recording started with the new parser and about 7 s and 10 s with `WebJsonConverter`.

**Not adopted.** VBA-FastJSON with `Scripting.Dictionary` took 1.60 of `WebJsonConverter`'s time on the same corpus. With VBA-FastDictionary it was comparable to or slightly faster than `ParseJsonText` (measured in a separate workbook), but that dictionary's class is named `Dictionary` and would replace `Scripting.Dictionary` for the whole user project, it adds two modules to the three-file distribution, and VBA-FastJSON uses pointer-based memory access. The experiment also showed that most remaining parse time is spent creating `Scripting.Dictionary` objects, so further gains would require fewer objects rather than a faster scanner.

## Chapter 8 — Multi-Layer Self-Healing Architecture

The engine’s resilience comes from choosing recovery behavior according to the failure layer, and from refusing recovery when retrying could duplicate a state-changing operation.

## [L1: Communication] WinSock Reconnection with Exponential Backoff

Transport recovery now rebuilds a native WinSock WebSocket session. If the socket enters `StateError`, `AttemptRecovery` waits with exponential backoff, then reconnects to the last driver-issued WebSocket URL. The recovery lock is the instance field `m_isRecovering`, acquired before any yielding work and released through a common cleanup path so nested recovery cannot strand the communicator.

Recovery backoff may pump Office messages, but this is protected by a second invariant: normal I/O entry points reject work while recovery owns the lifecycle, and only `AttemptRecovery` can temporarily authorize the internal `Connect` call. `Disconnect` and `ForceClose` set `m_recoveryCancelRequested`, allowing an explicit teardown to interrupt the backoff before a new socket is opened. Recovery reconnects preserve the event FIFO and session drop counters; a direct connection starts a fresh diagnostic session.

The invariant remains strict: recovery may establish a new socket, but it never replays the payload that failed. Request replay belongs to the wrapper, and only when the operation is safe to retry with a fresh ID.

At the wrapper level, however, a transport reconnect is terminal for the bound session. Subscription ownership belongs to the BiDi session, but event delivery does not survive a reconnect (measured with msedgedriver): the new connection answers commands while no longer delivering the events that `ConnectTo` subscribed. A silently healed transport would therefore let lifecycle tracking, completion signals, captures, and SPA waits run blind. The communicator increments `ConnectionGeneration` on every successful OPEN, including `AttemptRecovery` reconnects. The wrapper detects the changed generation and raises `ERR_SESSION_CONTINUITY_LOST` instead of continuing (Chapter 18). Wrapper-level automatic session recovery is deliberately not implemented; the caller must start a new session. The communicator's `AutoReconnect` still defaults to True and the wrapper does not change it, so a bound session can still spend one recovery backoff and open a connection before the wrapper reports the loss. This is deliberate: teardown releases the session-continuity binding first so that its best-effort browser-side cleanup can still use the communicator's recovery path on a degraded connection (Chapter 18).

## [L2: Addressing] Context Topology Reconstruction

For retryable context-loss conditions on a continuous session, `ExecuteBiDiCommand` refreshes the browsing-context tree and patches context/realm fields only when retargeting is permitted. Recovery refreshes the main binding only when `allowContextRetarget=True`, so explicit-context commands never depend on main-context availability merely to continue recovery. Explicit non-main targets and context-destroying commands are protected from unsafe retargeting. State-changing callers stop on ambiguous outcomes because context loss may be the visible side effect of an action that already succeeded. When a caller passes `allowAmbiguousRetry=False`, the stop occurs before the retargeting stage for both ambiguous statuses and `ERR_BIDI_PROTOCOL`, so such a command is never re-dispatched even when retargeting is nominally permitted. Deterministic pre-send rejections — 606, 607, and `WS_ERR_INVALID_UTF16` (9251) — are not routed into recovery at all. Session-continuity loss is checked earlier still: every dispatch first asserts continuity, and a failed dispatch on a lost or reconnected transport is converted to `ERR_SESSION_CONTINUITY_LOST` before any context recovery is attempted. Since v6.7 the same priority holds inside recovery: if the context refresh itself raises `ERR_SESSION_CONTINUITY_LOST`, or exhausts the wait budget, that result replaces the triggering error (the trigger is kept as `trigger=` in the description) instead of being appended as an ordinary "Recovery failed" note.

Chromium can report an in-flight main-realm command destroyed by navigation as `unknown error: Inspected target navigated or closed`. v6.7 does **not** add this phrase to the global `IsContextLostError` classifier, because explicit-window readiness checks and iframe `locateNodes` polling already consume the raw phrase as a transient condition. Instead, a private exact-match helper promotes it to Context Lost only when `allowContextRetarget`, `allowRecoveryRetry`, and `allowAmbiguousRetry` are all True — the combination in which the wrapper can safely refresh the main target and resend. Otherwise the raw response is preserved for the pre-existing transient, polling, and ambiguous-dispatch classifiers. `IsTransientWindowContextReadError` also accepts the wrapper's `Environment desync (Context Lost)` text in case main-context recovery is exhausted. O3 testing forced this response with an in-flight Promise, observed `[RECOVERY]` on the first attempt, and returned successfully from the new document; explicit iframe O1/O2 retained their previous non-retargeting behavior.

When a `MasterWaitEngine` command deadline is active, this same recovery loop is budget-bound. Every retry recalculates its send timeout, the 800×attempt recovery backoff is capped to the remainder, and a backoff that consumes the budget skips `UpdateMainContextId` and re-dispatch. T4c A-short exercised that path directly: it entered recovery after a navigation-induced Context Lost and returned tagged logical timeout at 1018 ms rather than spending the full recovery delay beyond a 1000 ms wait budget.

## [L3: Environment] JIT SPA Probe Re-injection

The SPA probe is rebuilt not only when navigation removes it, but also when its version or one of its Fetch, XHR, observer, or input-setter health checks fails. `browsingContext.navigationStarted` provides a one-shot hint for the affected context, allowing the wrapper to skip passive missing-probe cycles once the ordinary status query confirms the probe is unavailable or unhealthy.

Generation-safe network wrappers ensure that a stale Probe layer left inside page-owned telemetry instrumentation becomes a pass-through rather than a second counter. Runtime filter revisions are pushed independently, so a healthy Probe can accept new ignore arrays without rebuilding its hooks.

## [L4: Final Judgment] Circuit Breakers

Circuit breakers remain targeted rather than global panic switches. CDP command/session failures trip a CDP-side fatal reset after repeated failures. Recorder dispatch errors and SPA-probe recovery exhaustion have their own breakers. The socket layer has its own state transition to `StateError`, after which AutoReconnect can release stale handles and rebuild the transport. For a bound wrapper session, both the `StateError` transition and a rebuilt transport are reported as `ERR_SESSION_CONTINUITY_LOST`.

## Chapter 9 — ExecuteBaseAction — A Three-Phase Execution Pipeline

The core execution pipeline used by the main action family (click, bulk input, select by value, select by visible text, and lazy scroll). Click is a synthetic `element.click()` by default, with a trusted pointer click available as an opt-in ("Click Strategy" below); the other actions run as synthetic JavaScript. Some specialized paths — native key input, file selection, and the uninterrupted `input_keys` sequence — deliberately use dedicated implementations.

## Three-Phase Architecture

- **Phase 1: TryPreparePhase (Environment Preparation):** Responsible for setting up the environment before an interaction executes. On a retry (`retryCount > 0`), it refreshes only the addressing state owned by the action target. If the target is the pinned main context, it calls `UpdateMainContextId(forceRefresh:=True, Silent:=True)`. If the target is an explicit non-main context, it invalidates only that context's validation-cache entry and revalidates the same ID through `ResolveTargetContext`, preserving the Chapter 5 rule that explicit-context work must not depend on main-context availability.
- **Phase 2: TryExecutePhase (Execution):** Dispatches the action through `CallScript`, which applies `WrapInSafetyShell`. For click, with the default `UseTrustedClick=False`, the click is a node-addressed synthetic `element.click()` through `CallScript`. With `UseTrustedClick=True` the click goes through `PerformTrustedClick` with synthetic fallback allowed: an on-target click is a BiDi `input.performActions` pointer sequence outside the Safety Shell, and a target that is not topmost falls back to the synthetic `CallScript` route. Errors from either route are captured into the phase’s output fields.
- **Phase 3: TrySyncPhase (Post-Action Synchronization):** Runs network-idle and DOM-stability validation via `SyncAfterAction`. A failure in this phase does not invalidate the success of the action itself (best-effort). The exceptions are `ERR_CONSENSUS_HALT` and `ERR_SESSION_CONTINUITY_LOST`, which are re-raised to the caller as described in Chapter 3.

## Click Strategy: Synthetic by Default, Trusted Opt-In (v6.9)

Since v6.9 a click addresses the node directly with `element.click()` unless `UseTrustedClick` is set to `True`. With `True`, a click follows the usual browser-automation pattern: deliver a native pointer click when a person could make it, and address the node directly only when they could not. `UseTrustedClick` defaults to `False` and governs every click that goes through the `click` action key: `ExecuteClick` and the trigger and option clicks of `ExecuteSelectValue` on custom dropdowns. Two clicks stay synthetic regardless of the setting. The focus click before native key input uses its own `focus_click` key, because a pointer click places the caret at the click point: with an 80-character value and no `selectAllFirst`, a trusted focus click put the typed key after the 20th character, while the synthetic click left it at the end as in v6.5. `ExecuteRegisterAutoClicker` is the other: its preload script clicks in-page with `element.click()` without a VBA round trip, which a trusted click cannot do. `UseTrustedClick=True` restores the trusted-default behavior of v6.6–v6.8.

The default has changed twice. Before v6.6 it was the synthetic `element.click()`; the code justified it as the proven path on Wiz/Lit SPAs and said trusted pointer clicks could leave focus state that breaks some autocomplete flows. v6.6 made trusted clicks the default because that breakage had not been reproduced on Google Flights or on the other samples, and because the synthetic path has two weaknesses: it checks only `isConnected`, so a hidden node receives the click and the action succeeds, and it dispatches only `click`, so a control that listens to `pointerdown`/`mousedown` or rejects untrusted events does not react. Those weaknesses still apply to the default path in v6.9; they are the reasons to opt in to trusted clicks for a specific site. v6.9 returned to the synthetic default after the Google Flights failure described at the end of this section.

`PerformTrustedClick` scrolls the target to the center and hit-tests its center with `elementFromPoint`, descending through open ShadowRoots. On `hit=1` it sends a BiDi `input.performActions` pointer sequence. When the caller allows synthetic fallback, `hit=0` or a non-ambiguous `input.performActions` failure falls back to `element.click()` on the node through `CallScript`, and `hit=0` is recorded as `[TRUSTED-HITTEST]` ("Trusted Hit-Test Diagnostics" below). An ambiguous dispatch failure (timeout or connection loss after send) and an indeterminate hit test always raise, so a click is never sent twice.

| Caller | Synthetic fallback |
| :--- | :--- |
| `click` action key (`UseTrustedClick=True`, opt-in) | allowed |
| `ExecuteDownloads` | allowed |
| `ExecuteOpenNewContext` | refused (`TrustedClickRequired`) |
| `ExecuteSetFileSelectionViaDialog` | refused (`TrustedClickRequired`) |

Opening a context and opening a file chooser need genuine user activation. A single download link does not, so `ExecuteDownloads` keeps the fallback. A local Chromium fixture forced three covered triggers through the synthetic fallback in one batch; all three produced `downloadWillBegin`, all three correlated to terminal `downloadEnd`, and all three completed (`expected=3`, `started=3`, `complete=3`, `canceled=0`). Automatic-download gating was therefore not observed for that three-trigger case.

The fallback is what keeps trusted clicks safe on real pages. In Main03 (Jorudan, Edge, v6.6 trusted-default build) typing the destination opened its suggestion list over the search button. The hit test reported `[TRUSTED-HITTEST] hit=0 | reason=covered | top=DIV#t_sg6 [Higashi-Shinjuku]`: a pointer click at that point would have selected the Higashi-Shinjuku suggestion. The fallback clicked the search button itself and the search ran with the intended destination. In the same verification Main07 (ServiceNow) clicked the Sign in button inside Shadow DOM on target, Main08 (Google Flights) ran on target throughout, and the other samples produced no fallback.

Measured on Google Flights (Main08, Edge, 2026-10-04, v6.5 with both settings): both modes reached the same search URL. Trusted clicks delivered `pointerdown`, `mousedown`, and `click` with `isTrusted=true`, landing on inner `DIV`/`SPAN` children of the target; synthetic clicks delivered only `click` with `isTrusted=false`. The autocomplete breakage described in the code comment was not reproduced on this flow. In an A/B of the Search click alone (three trials per mode, alternating, a fresh browser per trial, setup clicks always synthetic) the SPA wait was 2.8–3.1 s synthetic and 2.6–2.7 s trusted. The part after the `GetShoppingResults` response did not differ; the request-to-response interval was about 1.1–1.2 s synthetic and 0.6–0.7 s trusted, for a reason not determined.

Measured on Google Flights again (Main08, Edge, 2026-10-10, v6.8 trusted default): every click in the flow, including Done and Search, executed and the browser reached the `/travel/flights/search` URL with the entered route and date, but the results area showed "Oops, something went wrong" in 3 out of 3 runs. With `UseTrustedClick=False` on the same build the results were displayed. Restoring synthetic clicks for only some of the clicks still left the "Cheapest" recalculation broken, so the failure is not tied to one click. The 2026-10-04 measurement above compared the search URL and the SPA wait, not the content of the results area, so the two measurements do not contradict each other. The cause was not isolated: the trusted pointer sequence moves to the target center with `duration=0`, which a site's behavior analysis may reject, and the different event and focus order may leave form state that the search request does not reflect, as the pre-v6.6 code comment warned. This result is why v6.9 restored the synthetic default. Whether a site breaks under trusted clicks cannot be detected at click time, because the command succeeds and the failure appears only in application state; the practical check is an A/B run with `UseTrustedClick` set to `True` and `False`, compared through the target response in the Discovery Log and the business-level result.

## Trusted Hit-Test Diagnostics (v6.5)

`HitTestJs` returns one of:

| Verdict | Meaning |
| :--- | :--- |
| `hit=1` | the center hits the target or a node inside it |
| `hit=0;zero-box` | the target has no box |
| `hit=0;no-element` | `elementFromPoint` returned null, for example when the center lies outside the viewport |
| `hit=0;covered;<front element>` | another element is topmost; tag, id, up to two classes, and the first 30 characters of `aria-label` or text |

`RequireTrustedHitTestResult` matches `hit=1` exactly and `hit=0` alone or as a `hit=0;` prefix; anything else still raises `TrustedClickHitTestIndeterminate`. The reason never affects the decision, and the `hit=1` path adds only a null check. On `hit=0`, `PerformTrustedClick` writes through `LogSignalLine`:

```
[TRUSTED-HITTEST] hit=0 | reason=covered | top=DIV#veil.veil.cover [Cookie notice] | outcome=synthetic-fallback
```

`outcome=refused` marks callers that disallow the fallback; their `TrustedClickRequired` message carries the reason in parentheses. A local fixture verified all three reasons, the absence of a line for an on-target click, and `outcome=refused` from `ExecuteOpenNewContext` (15/15).

## Native-Key Replacement Input (`selectAllFirst`, v5.0)

`ExecuteInputValue` exposes `selectAllFirst` for the dedicated native-key path. When `useNativeKeys:=True` and `selectAllFirst:=True`, the wrapper first focuses the resolved target and prepends a native `Ctrl+A` chord before the requested key sequence. This provides a browser-visible replacement gesture for controls that depend on real keyboard events, while preserving the ordinary native-input sequence when the option is omitted.

The option defaults to `False`, so existing callers are unchanged. It is meaningful only on the native-key branch; synthetic JavaScript/key-event input does not use this chord builder. Existing `WebKeyboard` special-key constants can still be appended to the requested value, allowing sequences such as `Ctrl+A -> text -> Enter` without introducing a separate public keyboard API.

## Retry Decision Logic

Each phase returns error information via Out parameters. `ERR_ACTION_FAILED` (for example, element-not-found) is propagated without retry, with one exception: a stale-element failure is retried after the element is re-resolved from its locator. A stale failure is either a Safety-Shell JavaScript error (`STALE_ELEMENT`, `STALE_ELEMENT_PRE_INPUT`, or `Element is no longer connected.`) or a protocol error reporting a stale reference, missing node, or detached node. The action scripts raise the stale error before any click or event dispatch, and the protocol rejects a stale reference before the function runs, so this retry cannot duplicate a page-visible effect. Before an ordinary stale/transient retry, the pipeline yields through `WaitHeartbeat(500)`. That heartbeat asserts session continuity, so a phase failure caused by a lost or reconnected transport surfaces as `ERR_SESSION_CONTINUITY_LOST` instead of being retried.

A separate ambiguous-outcome guard blocks retries when the browser may already have performed the action. The ambiguous statuses are 608 (the matching command response, or an unclassifiable message received during correlation, exceeded `MaxIncomingSize` and was discarded), 604, 601, 600, and 517. `ERR_BIDI_PROTOCOL` is also treated as ambiguous when its description indicates context loss or a destroyed execution context. The guard covers two kinds of action key: non-idempotent keys (`click`, `input`, `input_keys`, `select`, `select_text`), whose replay could duplicate user- or server-visible state, and `lazy_scroll`, which does not change application state but must not overlap a surviving earlier run because that run can reset page geometry while the retry is still measuring `scrollHeight`.

A consequence of this guard remains possible for clicks that navigate immediately in an explicit (non-main) context. If the document is replaced before a synthetic `script.callFunction` response arrives, the command can return context loss; because explicit contexts are never retargeted and a click is non-idempotent, the wrapper must treat the result as outcome-unknown rather than replay the click. A v6.6/v6.7 local fixture exercised four immediate-navigation cases — trusted/synthetic × main/explicit context — and all four returned `actionErr=0` with `navigated=True`; the ambiguous post-dispatch failure was **not reproduced** in that fixture. The no-replay rule is nevertheless retained because the timing remains browser/page dependent.


The bulk-input helper applies the same rule to its `input_keys` fallback. It may fall back only after a **confirmed, non-ambiguous** bulk-input failure such as `ACTIVE_INPUT_NOT_STABLE`. `ERR_CONSENSUS_HALT`, `ERR_SESSION_CONTINUITY_LOST`, and every failure classified by `IsAmbiguousDispatchFailure` are re-raised without dispatching `input_keys`, because the original browser-side `input` task may still be running. The error-handler transition uses `Resume` to leave the active VBA handler before fallback logic begins, so a later fallback failure can be handled normally; when that fallback fails, the final description preserves the original bulk-input failure as diagnostic context.

## Post-Action Synchronization Observability

A successful browser action and a successful post-action wait are intentionally separate facts. At each top-level action boundary the wrapper resets a session-scoped result record, then exposes it through `LastSyncAttempted`, `LastSyncSucceeded`, `LastSyncErrorNumber`, `LastSyncErrorSource`, and `LastSyncErrorDescription`. Every absorbed synchronization failure, whether a DOM-only timeout or an infrastructure error, can therefore be inspected by the caller without redefining the already-completed browser action as failed. `ERR_CONSENSUS_HALT` and `ERR_SESSION_CONTINUITY_LOST` remain the exceptions and propagate immediately after being recorded.

## Specialized File Selection Paths

File handling is intentionally described as **selection**, not upload. WebDriver BiDi `input.setFiles` changes the selected files of an HTML file input. Whether the application subsequently uploads those files, validates them locally, previews them, transforms them, or waits for another user action is outside the protocol command itself. Application completion must therefore be judged separately.

`ExecuteSetFiles` is the direct path for a stable file input that can be located before selection. The wrapper resolves the target to a `sharedId`, normalizes one or more file paths, sends `input.setFiles`, validates the protocol response, and — when `waitNetworkIdle` is enabled — performs the ordinary required SPA synchronization. The `input.setFiles` command is marked non-replayable on ambiguous outcome.

`ExecuteSetFileSelectionViaDialog` is the short-lived-input path for an XPath trigger. A completion signal is strongly recommended once the site’s completion condition is known, but it is not required before entry. If one or more signals are armed, the trigger and consuming completion wait must use the same browsing context as their owner. With no signal, the method intentionally falls back to an ungated idle-only final wait; when Discovery Log recording is active, that first pass supplies the DOM/network evidence from which a targeted arm can be chosen for the next run. The method then subscribes to `input.fileDialogOpened`, resolves the trigger, installs temporary Chromium native-picker suppression, drains buffered stale events immediately before the local capture arm, snapshots the **composite file-dialog-relevant loss total** (communicator `FileDialogEventLossCount` / `UnknownCriticalEventLossCount` plus wrapper dispatch-classified equivalents), and performs a trusted BiDi pointer click. No SPA wait is inserted after the trigger click: the transient file input must be captured and used before application state can replace it.

The captured event is a protocol contract, not merely a notification. `params.context` must match the owner context; `params.multiple` must be present; and `params.element.sharedId` must identify an HTML file input. Multiple selected paths are rejected when `multiple=false`. Only after these checks does the wrapper issue `input.setFiles`.

The final ordering is deliberate: `input.setFiles` first, local file-dialog capture reset second, native-picker interception release third, application completion wait last. The interceptor is needed only through the chooser/setFiles hand-off and should not remain active while waiting for the application to finish its own work.

Both the trigger click and `input.setFiles` are state-changing operations and are never blindly replayed after ambiguous outcomes. If `input.setFiles` has succeeded and interceptor cleanup fails, the method raises `PostSelectionInterceptionCleanupFailed` as a non-retryable result. If cleanup succeeds but the final SPA synchronization later fails, the error is wrapped as `PostSelectionCompletionFailed`, explicitly warning that file selection may already have started application work. This preserves the same rule used elsewhere in the wrapper: an uncertain post-action observation must not cause automatic duplication of an action that may already have succeeded.

## Specialized Download Batch Transaction Path

`ExecuteDownloads` runs the download-batch transaction engine. A single XPath is simply a batch with `expectedCount=1`; multiple XPath triggers may be supplied as an array or `Collection`. Download events are subscribed lazily, so sessions that never use download observation do not pay for them.

v4.9 added an opt-in cross-context mode to `ExecuteDownloads` through `allowCrossContext:=True`. The default remains `False`, preserving the strict historical rule that accepted download events must belong to the trigger/owner context. In cross-context mode, the first correlatable `downloadWillBegin` accepted by the batch latches its reporting browsing context; later accepted starts and terminal `downloadEnd` events must remain consistent with that latched download context. Correlation still prefers the browser-provided download UUID and can fall back to `context + navigation` when that UUID is unavailable.

Before any trigger is clicked, **all targets are resolved first**. The wrapper then drains buffered events, arms one owner-context batch, and snapshots the composite download-relevant loss total (communicator `DownloadEventLossCount` / `UnknownCriticalEventLossCount` plus wrapper dispatch-classified equivalents). Resolved triggers are dispatched sequentially through `PerformTrustedClick`, with event drains between clicks: a topmost trigger receives a trusted BiDi pointer click, and a trigger that is not topmost falls back to a synthetic click recorded as `[TRUSTED-HITTEST]` ("Click Strategy" above). The wrapper does not wait for each transfer to finish before dispatching the next trigger, so accepted downloads may overlap. A trigger whose click outcome is ambiguous is never replayed, and later triggers are not blindly dispatched after a structural failure.

The wait has two bounded stages using the same public `timeoutMs` value. **Stage 1** accepts exactly the expected number of correlatable `browsingContext.downloadWillBegin` transactions. Correlation prefers the browser-provided `download` identifier and falls back to `context + navigation` for measured implementations that omit it. **Stage 2** starts after the expected start set has been accepted and waits until every accepted transaction reports `complete` or `canceled` through `browsingContext.downloadEnd`. A browser-reported `canceled` is a terminal transaction result; the outer batch reports `status="failed"` when any accepted transaction is canceled.

Structural uncertainty raises instead of returning an ordinary failed batch: start/completion timeout, more correlatable starts than expected (`DownloadBatchCountMismatch`), duplicate non-empty `suggestedFilename` within the batch (`DownloadBatchFilenameCollision`), relevant asynchronous event loss after the arm boundary, or an ambiguous trigger/protocol failure. Once a filename collision is observed, remaining triggers are not dispatched because two browser transactions may target the same destination path.

The returned outer `Dictionary` contains `status`, `expectedCount`, `dispatchCount`, `startedCount`, `terminalCount`, `completeCount`, `canceledCount`, `context`, `asyncEventsDroppedSinceArm`, and a nested `downloads` dictionary. Each nested transaction contains fields such as `correlationKey`, `correlationMode`, `context`, `downloadId`, `navigationId`, `suggestedFilename`, `url`, `state`, `startedSeen`, `endSeen`, `status`, and `filePath`. `filePath` remains browser-reported diagnostic output; the method does not claim that the artifact still exists, has reached a stable size, or has a verified hash on disk.

The Discovery timeline uses the v4.4 batch family, including `[DOWNLOAD-BATCH-ARM]`, `[DOWNLOAD-BATCH-START-ACCEPTED]`, `[DOWNLOAD-BATCH-END-MATCHED]`, `[DOWNLOAD-BATCH-CTX-MISS]`, `[DOWNLOAD-BATCH-WILL-BEGIN-IGNORED]`, `[DOWNLOAD-BATCH-END-IGNORED]`, and `[DOWNLOAD-BATCH-FILENAME-COLLISION]`, alongside the raw `[DOWNLOAD-WILL-BEGIN]` and `[DOWNLOAD-END]` observations.

## Chapter 10 — PostScript — A Fire-and-Forget Communication Model

Whereas `CallScript` and `ExecuteBiDiCommand` wait for a matching response, `PostScript` is a send-only, best-effort pathway. The underlying send goes through the WinSock frame queue, but VBA still does not enter the response-correlation loop.

## Design Principle

`PostScript` uses the fixed reserved ID `2`, outside the normal command ID range. Replies for reserved-band IDs are consumed by the communicator and never exposed as application events. The pathway calls `SendMessage` with `allowRecovery:=False`; if the send fails, it is dropped. Recovery must not replay a disposable message because doing so would violate the fire-and-forget contract.

Because `SendMessage` can now raise on invalid caller text, the communicator's `PostScript` absorbs send-stage errors locally, and an oversized payload is dropped with a critical trace instead of raising. The wrapper's public `PostScript` has no handler of its own: steps before the send, such as target-context resolution, can still raise to the caller. The destructor path that uses it wraps the call in `On Error Resume Next`, so teardown itself never raises.

## Current Use

The concrete use remains teardown. `Class_Terminate` may attempt to remove the browser-side HUD without waiting for an acknowledged response, reducing the risk that object destruction performs a final blocking wait. Normal HUD state updates remain on acknowledged `CallScript` and are controlled by deduplication and telemetry gating.

## Chapter 11 — Input Sanitization and Parameter Defense

A cross-cutting defense mechanism used by timing-sensitive public methods and wait helpers.

## The SanitizeMs Function

`SanitizeMs` replaces zero or negative values with the caller-supplied default, applies a configurable minimum floor (50 ms by default), and caps the result at 600,000 ms (10 minutes). This prevents Boolean `True` (`-1`) and other invalid values from leaking into wait loops while bounding accidental long hangs. `WaitForNetworkIdleSpa` is a deliberate exception for backward compatibility: `0` silently selects the default, and positive values use a 1 ms floor instead of 50 ms.

That 600,000 ms ceiling applies to timeout inputs used by browser operations and wrapper waits, not directly to transport response ownership. `ResolveTransportTimeout` normally adds a 5,000 ms response margin, raises the result to at least 30,000 ms (`DEFAULT_COMMAND_TIMEOUT_MS`), and then clamps against the communicator’s `MaxCommandCorrelationWaitMs = 605000`. Navigation additionally enforces a 60,000 ms transport floor. Chapter 13 describes why those budgets are intentionally separate.

## The Entry Guard Pattern

When `waitNetworkIdle` is True, public entry guards replace non-positive stability/timeout inputs with the relevant defaults before synchronization begins. XPath and Shadow element resolution intentionally preserve an original `searchTimeoutMs = 0` as a one-shot immediate check, while negative values are sanitized to the ordinary default before the timed search begins. This keeps `0` as the only immediate-search sentinel across those two locator paths.

## The ResolveXPathOrThrow Pattern

Public methods that require element lookup immediately validate the result of `GetFindElementSharedIdByXPath` and raise `ERR_ACTION_FAILED` if it is an empty string. This way, operations on a non-existent element propagate a clear error to the caller instead of silently failing.

## Visible-First Candidate Selection (v6.5)

`browsingContext.locateNodes` returns every match in document order, and v6.4 used the first. Single-page applications often keep hidden copies of dialogs and menus, so a simple XPath can match an invisible element first. On Google Flights `//button[contains(., 'Done')]` matched a 0×0 button inside an `aria-hidden` subtree before the visible one. The synthetic click succeeded on the hidden node; with `UseTrustedClick=True` the hit test returned `hit=0` and fell back to a synthetic click.

When several nodes match and the action prefers a visible target, `PickFirstVisibleNodeIndex` passes up to 50 candidates to one `script.callFunction` and takes the first visible one; when none is visible, or the check fails, it takes the first match. A single match costs nothing extra. Visible means connected, with a client rect whose width or height is above 0, a computed `visibility` of `visible`, and no `[inert]` ancestor in the flat/composed ancestry. Since v6.7 the inert walk crosses slot assignment and Shadow boundaries (`assignedSlot` → `parentElement` → `getRootNode().host`) instead of relying on DOM-only `closest('[inert]')`. `opacity` is ignored because an `opacity:0` input under a styled label is a common legitimate target, and `aria-hidden` is ignored because it does not imply invisibility. `VisiblePredicateJs` holds this definition for both the XPath and the Shadow resolver.

| Path | Visible-first |
| :--- | :--- |
| click, input, `input_keys`, select, select by text | yes |
| triggers of `ExecuteDownloads`, `ExecuteOpenNewContext`, `ExecuteSetFileSelectionViaDialog` | yes |
| stale-element re-resolution in `ExecuteBaseAction`, input post-check | same rule as the initial resolve |
| `ExecuteSetFiles` | no (the file input is usually hidden) |
| readers, including `ExecuteIsElementVisible` | no (document order) |

`PrefersVisibleTarget(actionKey)` decides the rule, so an initial resolve and its retry never pick different policies. `ExecuteIsElementVisible` answers for the first match in document order: for the Google Flights XPath above it returns `False` while `ExecuteClick` clicks the visible duplicate. `PreferVisibleMatch = False` restores strict document order for every path.

A choice other than the first match is recorded on the timeline:

```
[LOCATE-PREFER-VISIBLE] matched=2 | checked=2 | chose=2 | xpath=//button[contains(., 'Done')]
```

The Shadow resolver appends `| shadow=1`. `ExecuteWizSelectDropdown`'s option search keeps its own visibility test, which also accepts an element that has client rects but no size; v6.5 does not change it.

A local fixture verified the rule on Edge with synthetic and trusted clicks (8/8 each): a `display:none` or `visibility:hidden` duplicate before a visible one, no visible match (first match), an `opacity:0` first match (kept), the preference turned off (first match), a reader (first match), and input into the visible field of two.

## Chapter 12 — Browser-Side HUD (Head-Up Display)

An in-browser HUD implementation that visualizes the synchronization-wait state in real time.

## Optimization

- **Deduplication & WebSocket-traffic suppression:** `currentHudKey` combines message and color; an unchanged state produces no `CallScript` request. The three SPA states are red **Synchronizing**, amber **Awaiting signal**, and green **Stable**.
- **Context-change detection:** A different `targetCtx` clears the fingerprint so the HUD is re-emitted in the new context.

`pointer-events: none` ensures the HUD does not obstruct automation click operations. Using the CSS ID `vba-bidi-hud` — and including it among the target selectors of the noise filter — ensures that the HUD’s own DOM changes do not become noise for the SPA probe.

## Chapter 13 — Decoupled Heartbeat and Connection Keep-Alive

The transport has two independent liveness layers: WebSocket-level ping/pong inside the RFC 6455 engine, and an application-level BiDi `session.status` heartbeat in `GetMessage`.

## Receive Polling and Heartbeat Pacing Are Separate

The receive path keeps its `DEFAULT_POLLING_INTERVAL_MS = 100` cadence so asynchronous events can be observed promptly. The public `PollingInterval` setting is clamped to `[10..5000]` ms: the lower bound prevents an accidental hot loop, and the upper bound stays within the application-heartbeat timeout. Application heartbeat traffic is no longer coupled to every idle poll.

`GetMessage` follows this order:

1. **Buffered event first:** return the oldest event already captured during command/response correlation.
2. **Completed-message drain:** consume any already assembled WinSock text messages before performing more native work.
3. **Bounded receive Pump:** after the 100 ms poll interval has elapsed, run one bounded `WsPump` pass. A real event suppresses heartbeat generation for that call.
4. **Independent heartbeat pacing:** only when no real event is ready, no application heartbeat is already outstanding, and at least `APPLICATION_HEARTBEAT_INTERVAL_MS = 1,000` ms has elapsed does the communicator send `session.status`.
5. **Reserved reply handling:** heartbeat IDs rotate through `[3..99]`; their replies are consumed internally at both receive sites and are never exposed as application events.

At most one application-level heartbeat can be outstanding. This avoids consuming the reserved ID band or generating a stream of overlapping `session.status` commands when the driver is slow.

`IdleReceive` (Chapter 2) does not change this order: it only enqueues completed events, which `GetMessage` later returns through step 1. Because step 1 returns buffered events without reading the socket, a long backlog drain can leave the socket unread for a while; this affects only the precision of arrival times (Chapter 3), not ordering or correctness. Reading the wire before returning buffered events was considered and deliberately not adopted, to keep the v4.6 fairness-bounded drain behavior unchanged.

## Heartbeat Timeout Escalation Requires Repetition

If the outstanding heartbeat reply is not observed within `APPLICATION_HEARTBEAT_TIMEOUT_MS = 5,000` ms, the communicator writes a critical trace, retires that heartbeat ID, increments the consecutive application-heartbeat-timeout count, and allows a later heartbeat to use a new ID. A single missed `session.status` reply therefore remains diagnostic rather than immediately condemning the socket.

v4.4 retains the bounded escalation rule `MAX_CONSECUTIVE_APPLICATION_HEARTBEAT_TIMEOUTS = 3`. When three heartbeat timeouts occur consecutively without intervening peer progress, the communicator records an application-liveness failure and transitions to `StateError`. Any assembled peer message clears the consecutive-heartbeat-timeout suspicion because it proves peer progress.

## WebSocket Ping/Pong Remains Independent

The RFC 6455 layer answers browser ping frames and issues its own client ping frames on a `15,000 ms` interval. Each client ping carries a four-byte sequence number, and only the pong echoing the currently outstanding sequence clears that state. If the send queue is busy, ping creation is deferred briefly rather than competing with application frames; at most one client ping remains outstanding. If the matching pong has not arrived `WS_CLIENT_PONG_TIMEOUT_MS = 10,000` ms after the ping was sent, the transport fails with internal code 9221. A silent peer is therefore detected at this layer only after up to about 25 seconds.

That mechanism validates WebSocket-level liveness; the `session.status` heartbeat validates application-level BiDi responsiveness. Neither mechanism replaces command deadlines or response correlation.

## The End of Blocking-Receive Silence

The old WinHTTP version had a fundamental limit: a TCP-alive peer that stopped delivering WebSocket frames could trap the synchronous receive call. The WinSock transport removes that class of freeze by replacing blocking receive with non-blocking `recv`, bounded `WsPump` slices, and command-level deadlines.

## Command-Correlation Deadline and the 605-Second Ceiling

v4.4 separates command-correlation timeout from transport failure. If the matching response does not arrive by the correlation deadline, error `604` (`CommandCorrelationTimeout`) is raised while an otherwise-open socket is preserved. The browser operation may still be running, so the timeout itself is not treated as proof that the connection is dead.

Public timeout inputs are capped at 600,000 ms by `SanitizeMs`. The wrapper normally adds a 5,000 ms response-correlation margin with a 30,000 ms minimum, and the communicator owns the final `MAX_COMMAND_CORRELATION_WAIT_MS = 605000` ceiling. This lets `CallScript(safetyTimeoutMs:=600000)` fit its configured safety timeout inside the response-ownership budget instead of being cut off by a shorter transport cap. A 604 is annotated with `PeerLiveness=responsive|unresponsive` from one bounded `session.status` probe (`CheckAlive`, 3,000 ms), because the transport's own ping/pong cycle may take up to about 25 seconds to notice a silent peer. The classification is diagnostic only; the command is not replayed. The budgets remain independent: if browser-side work continues longer — for example because cooperative `hb()` calls keep the watchdog alive — correlation can still expire with 604 while the browser task survives.

A secondary `CommandCorrelationOverrun` fail-safe sits at `correlationDeadline + 5,000 ms`. It is not an extended normal timeout; it exists to detect the receive/parser loop itself exceeding its bounded-work assumption. Crossing that secondary boundary transitions the communicator to `StateError`. When `AllowUiPump=True`, time spent executing Office/VBA callbacks is excluded from this hard-overrun judgment by extending the hard deadline by the callback duration.

With the default `AllowUiPump=False`, a very long synchronous correlation wait advances without Office `DoEvents`, so Excel may appear unresponsive for the duration. That is different from being trapped inside a blocking native receive: control remains in the bounded correlation loop. Callers that prefer UI responsiveness can explicitly opt in with `bidi.AllowUiPump = True`.

## Chapter 14 — MasterWaitEngine — Nested Wait State and Cleanup Safety

The high-precision polling engine that drives every wait operation.

## Nested Wait Depth Management (`m_waitStackDepth`)

Because wait operations may be nested, `m_waitStackDepth` tracks the active wait depth.

- **Root entry (**`depth = 1`**):** Initializes wait telemetry and the browser-side HUD only for the outermost wait.
- **Nested entry:** Reuses the existing wait state without repeatedly initializing shared diagnostics.
- **Normal completion:** Decrements the depth and performs final cleanup only when the outermost wait finishes.
- **Error completion:** Resets the depth to zero so that a failed inner wait cannot leave the wrapper in a permanently active wait state.

## Host-Neutral Wait Behavior

The wait engine drives no host-specific UI state. `Application.Interactive`, `Application.Cursor`, and `Application.StatusBar` are not touched, so waiting never locks the host application’s user interface. This improves compatibility with Microsoft Access while leaving WebDriver BiDi communication, SPA synchronization, timeout handling, telemetry, and recovery behavior unchanged.

## CleanExit Guarantee

Every exit path converges on the shared cleanup section. This ensures that the nested wait counter, browser-side HUD, telemetry state, and error propagation rules remain consistent after normal completion, timeout, or infrastructure failure.

## Session-Continuity Assertion in Waits

`WaitHeartbeat` and `WaitHeartbeatBounded` drain recorder events, pump Office messages, assert session continuity, and then sleep through `IdleReceive` so that events arriving between polls are enqueued with accurate arrival times. They assert session continuity after draining and pumping. An event-driven wait therefore stops with `ERR_SESSION_CONTINUITY_LOST` rather than continuing to wait for, or judge idleness from, events that the current transport can no longer deliver.

## Protocol-Aware Polling

Polling helpers no longer treat every protocol error as temporary. `browsingContext.locateNodes` may continue only for classified document/context churn such as `no such frame`, `no such node`, `stale element reference`, or narrowly matched navigation-destruction messages. `browsingContext.getTree` has an even smaller retry set. Malformed JSON, non-transient BiDi errors, and response-contract violations surface immediately.

When the time budget expires while the last polling result is still one of those retryable protocol errors, the wrapper raises `ERR_BIDI_PROTOCOL` with the final remote error summary instead of returning a misleading ordinary timeout or “not found” result. This keeps timeout tuning separate from browser-context failure diagnosis.

XPath polling also treats URL observation as advisory rather than authoritative. For a timed search, `GetFindElementSharedIdByXPath` takes a best-effort starting-URL baseline; `searchTimeoutMs = 0` skips that extra round trip entirely. Negative timeout inputs are sanitized to the ordinary default timeout before this decision and therefore remain timed searches. Every fifth polling iteration performs another best-effort URL probe. A temporary `script.callFunction` / context-loss failure in either probe does **not** abort element search; that URL check is skipped for the round and `browsingContext.locateNodes` continues under its own retry classification.

`about:blank` is not itself evidence that a target navigated away. A context that starts on `about:blank` may legitimately receive DOM later through script, so the search continues. Early termination for `about:blank` occurs only when the starting URL was successfully observed, that starting URL was not `about:blank`, and a later successful probe shows a transition to `about:blank`. A successfully probed empty URL still terminates the search. `about:srcdoc` is not part of this `about:blank` rule.

## Chapter 15 — Event Subscription Management

The design for efficiently managing BiDi protocol event subscriptions.

## Delta Subscription

`ExecuteSessionSubscribe` tracks already-subscribed event/context keys and performs a delta check that sends only new registrations. The key takes the form `eventName|contextId`, while the browser-returned subscription ID is retained as the remote ownership token used by `session.unsubscribe`.

## Retired IDs and Same-Session Cleanup

A context-scoped subscription can outlive the context key that originally requested it. When a context is destroyed, v4.4 removes dead `eventName|contextId` keys from the active delta registry but moves the associated server-issued subscription IDs into a **retired-ID registry** instead of forgetting them. Clear/shutdown cleanup deduplicates active and retired IDs and attempts `session.unsubscribe` while the BiDi socket is still usable.

If that unsubscribe cannot be confirmed because the transport is already gone or the acknowledgement is lost, the wrapper preserves only the issued subscription IDs together with a normalized BiDi **session identity**. On a later `ConnectTo` to the same WebDriver session, those deferred IDs are reconciled **before any fresh mandatory subscription is created**. A deferred record from a different session is discarded locally rather than sent to the wrong browser session. Deferred IDs are released one at a time, so an `invalid argument` reply unambiguously means that the ID is no longer known to the session and is accepted as confirmed cleanup; this covers the case in which the earlier unsubscribe succeeded and only its acknowledgement was lost. If another failure prevents confirmation, `ConnectTo` fails rather than proceeding over unresolved ownership. This prevents WebSocket teardown from silently orphaning session-side subscriptions whose IDs were issued to the wrapper. The asymmetry is deliberate: IDs issued on an earlier connection can still be unsubscribed from a later one, but event delivery for those subscriptions does not follow the session onto a new connection. A subscription whose `session.subscribe` response was itself lost cannot be covered, because its ID was never received.

## Network Events for Visibility and Recording

`ConnectTo` makes four low-volume lifecycle/diagnostic subscriptions mandatory: `log.entryAdded`, `browsingContext.navigationStarted`, `browsingContext.contextCreated`, and `browsingContext.contextDestroyed`. `ConnectTo` itself does not enable the high-volume network stream globally. `StartDiscoveryLog` subscribes the ordinary recorder events (`network.fetchError`, navigation lifecycle events, and `network.beforeRequestSent`) and ensures that the exact GLOBAL `network.responseCompleted` subscription is available continuously. An existing global subscription is reused; otherwise one is created through the wrapper-wide active-subscription registry. No Recorder-specific ownership ID is retained. Separately, `ArmNetworkSignal` ensures that `network.responseCompleted` is subscribed even when the recorder is off. `ExecuteIsUrlContains` also subscribes GLOBAL `network.responseCompleted`, `network.fetchError`, `browsingContext.load`, and `browsingContext.fragmentNavigated`. These method-driven subscriptions are not released when the method returns; they remain active until ClearState or Shutdown. After the first such call, response traffic from every context therefore flows into the event FIFO for the rest of the session even with the recorder off, which increases FIFO pressure and with it the chance that an arm-scoped capture observes event loss.

None of these events drives the idle counters — Fetch/XHR consensus remains browser-probe state. Network events are used for signal matching, `[REQ]/[RES]/[ERR]/[BLOCK]` recording, and noise classification. A network signal additionally requires the event context to equal the shared signal owner, except that an arm created with `allowContextless:=True` also accepts an empty context. Because `ArmNetworkSignal` subscribes GLOBAL `network.responseCompleted`, worker responses are delivered even when Discovery recording is off. A matching URL from another context is rejected and reported once as `[SPA-SIGNAL-CTX-MISS]`.

Beginning with v5.3, `ExecuteNavigateAndGetStatus` no longer pauses Discovery Recorder observation by unsubscribing GLOBAL `network.responseCompleted`. When Discovery recording is active, the event remains subscribed through navigation URL/readyState stability and subsequent SPA settlement. `network.beforeRequestSent` also remains live. This favors complete `[RES]` and BODY-candidate observation over the former traffic-reduction optimization.

Because the Recorder no longer creates that navigation-time gap, there is no pause/restore retry path at SPA-wait entry and no Recorder-specific restore ownership to reconcile. Subscription cleanup remains the responsibility of the wrapper-wide active/retired subscription registries during ordinary clear and shutdown handling.

`network.beforeRequestSent` is recording-only and emits the `[REQ]` start marker; it is never wired into consensus. Because a request-start event has no response MIME type, `[REQ]` filtering is URL-only. A later `[RES]` can be filtered by URL or MIME, while a request can instead end as `[ERR]`/`[BLOCK]`, remain incomplete when recording stops, or disappear with a truncated log head. v5.3 continues to track request **hops** by `(requestId, redirectCount)` and emits `[REQ-UNPAIRED]` at Stop. Its categories are now `open-at-end` and `other`; the legacy `pause-exposed` category is gone because Discovery no longer deliberately suspends `responseCompleted` observation.

BODY capture, introduced in v4.8 and refined through v5.2, remains separate from these event subscriptions. `network.addDataCollector` registers browser-side retention for response data by default and for request data only when explicitly requested. `network.beforeRequestSent` and `network.responseCompleted` still provide candidate metadata and request IDs, but the payload itself is not synchronously fetched at event-dispatch time. `network.getData` is deferred to Discovery shutdown so body analysis cannot perturb the live wait/control loop. The current log-side default additionally requires top-context + same-origin/same-site/none Fetch Metadata unless an explicit BODY allow-list pattern is used.

## File-Dialog Event Subscription

`input.fileDialogOpened` is not part of the mandatory `ConnectTo` subscription. `ExecuteSetFileSelectionViaDialog` delta-subscribes it before enabling native-picker interception and before the trusted trigger click. The protocol subscription is session-scoped and may remain active afterward; a separate one-shot local arm (`m_fileDlgArmed`) determines whether an event belongs to the currently executing file-selection operation.

In the tested Chromium path, `input.fileDialogOpened` is commonly received while `input.performActions` is still inside command-response correlation, so `SendAndReceive` preserves the event in the bounded FIFO and the first later queue drain can consume it immediately. This relative ordering is **not** treated as a WebDriver BiDi guarantee. The implementation does not depend on it: if the chooser event arrives after the `input.performActions` response, `WaitForFileDialogCapture` continues draining until the event is observed or `fileDialogTimeoutMs` expires.

After the fresh CDP session has been resolved and native-picker interception has been enabled, but immediately before the local arm is raised, the wrapper drains buffered events through `ProcessRecorderQueue`. This placement also dispatches asynchronous events preserved during those CDP command round-trips while the local file-dialog arm is still down. It is not a formal queue watermark, but it materially reduces the window in which an ordinary stale chooser event could satisfy a new operation. The wrapper then snapshots the **file-dialog-relevant loss total** at the arm boundary: `FileDialogEventLossCount + UnknownCriticalEventLossCount`. Once armed, the handler accepts exactly one matching-context event. Missing-context events are ignored, the first foreign-context event is logged as `[FILE-DIALOG-CTX-MISS]`, and a valid event is recorded as `[FILE-DIALOG-HIT]` with `hasElement` and `multiple` diagnostics. `[FILE-DIALOG-ARM]` and ignored-event diagnostics use the same signal logging path as SPA completion-gate evidence, so they enter the Discovery Log when recording and the Immediate Window when wrapper debug mode is enabled.

While capture is active, any increase in the composite file-dialog-relevant loss total is treated as a correctness failure, not merely as timeout context. `WaitForFileDialogCapture` raises `ERR_BIDI_PROTOCOL` immediately with `AsyncEventsDroppedSinceArm=<n>` because an evicted, oversized, malformed, dispatch-dropped, or otherwise unclassifiable critical event makes exact capture unknowable. `FileDialogTimeout` is raised only when the time budget expires with no accepted chooser event and no detected relevant loss. This v4.4 distinction prevents a timeout from being misread as proof that the chooser never opened when the event path itself may have lost evidence.

v6.7 diagnostic testing also measured the lifetime of the element shared reference carried by `input.fileDialogOpened`, independently of the native-picker interceptor. The test captured the file-input `sharedId`, disabled interception, retained only that reference, and then called `input.setFiles`. The same live document succeeded immediately, after 5 s, and after 30 s; no short time-based expiry was observed through 30 seconds. Replacing the document in the same browsing context invalidated the old reference with `no such node`, while a freshly resolved file input on the new document succeeded. Destroying the owning tab/context rejected the old reference as Context Lost, and the surviving main context still answered a subsequent script call. The practical rule is therefore document/context lifetime, not a measured short TTL: do not carry a captured file-input reference across document replacement or context destruction.

## Lifecycle and New-Context Event Subscription

`browsingContext.contextCreated` and `browsingContext.contextDestroyed` are mandatory `ConnectTo` subscriptions in v4.4. They maintain the validated-context cache, drive pinned-main-context loss detection, and support `ExecuteOpenNewContext`. The wrapper’s topology decision uses a composite lifecycle-loss total that combines communicator-classified loss with wrapper dispatch-classified lifecycle/unknown-critical loss before trusting cached context state.

## Download Event Subscription

`browsingContext.downloadWillBegin` and `browsingContext.downloadEnd` are subscribed lazily by the download engine behind `ExecuteDownloads`. A session that never uses download observation does not enable them. The local batch arm is owner-context scoped, records the expected trigger count, accepts only correlatable starts, and treats any increase in the composite download-relevant loss total as a hard observation failure. Raw and batch-level download diagnostics are still logged even when events are foreign-context, uncorrelatable, duplicate, or otherwise ineligible to satisfy the active batch.

## Chapter 16 — Navigation Engine

A pure-BiDi navigation design that performs page transitions safely and efficiently.

## State Management in ExecuteBrowsingContextNavigate

At the start of navigation it resets only transient navigation state, capturing the target URL’s origin (`preNavOrigin`) so that a redirect-induced cross-origin transition can be detected against the post-navigation URL returned in the BiDi response. There is no in-flight network counter to clear — consensus no longer maintains one — so the former one-shot reset of an inflight dictionary has been removed.

`m_mainContextId` is retained to avoid an unnecessary rediscovery trip. The reusable `m_cdpSessionId` cache remains associated with main-context CDP features such as resource blocking, so a redirect-induced cross-origin result clears it for lazy re-acquisition; same-origin navigation keeps it. The file-chooser path does **not** rely on that cached session: it resolves a fresh CDP session from the exact target BiDi context for each chooser operation, which avoids silently applying interception to the wrong OOPIF or popup. Explicit non-main navigation is also marked non-retargetable, preventing context recovery from driving the surviving main tab to the requested URL. Main-context navigation passes retargeting as permitted, but because the dispatch uses `allowAmbiguousRetry=False`, a context-loss response stops before the retargeting stage (Chapter 8); in practice no navigation is re-dispatched after context loss.

## BiDi Wait-Level Selection

For the wait parameter of `browsingContext.navigate`, we use “interactive”. This is a two-stage design: obtaining the protocol response early while performing more precise stability judgment on the VBA side via MasterWaitEngine. The post-navigation stability wait applies the same escalation discipline as Chapter 3: an `ERR_CONSENSUS_HALT` raised inside the navigate path is re-raised to the caller rather than absorbed, so a navigation that never settles on the network side halts loudly instead of returning a false success. Unlike `TrySyncPhase`, `SettleAfterNavigation` propagates only `ERR_CONSENSUS_HALT`. A session-continuity loss during settlement is recorded in `LastSync*` and absorbed; the navigation method may still return an already captured HTTP status (or an empty string with `requireHttpStatus=False`), and the loss surfaces as `ERR_SESSION_CONTINUITY_LOST` on the next command or wait. Callers that must not proceed on a lost session should check `LastSyncErrorNumber` or call `CheckAlive` after navigation.

v4.6 also makes the URL-stability phase **queue-fair**. Its heartbeat uses the bounded non-blocking recorder drain rather than a full queue flush, and the SPA idle wait begins with the same bounded pre-drain. Large event bursts can therefore be serviced incrementally while URL/readyState polling and synchronization continue to make forward progress.

## ExecuteNavigateAndGetStatus — HTTP-Status Correlation and Retry Structure

`ExecuteNavigateAndGetStatus` still allows up to two retries (three loop attempts total), but only for explicitly classified Chromium network failures: `net::ERR_CONNECTION_RESET`, `CONNECTION_CLOSED`, `CONNECTION_ABORTED`, `CONNECTION_REFUSED`, `CONNECTION_FAILED`, `CONNECTION_TIMED_OUT`, `EMPTY_RESPONSE`, `SOCKET_NOT_CONNECTED`, `ADDRESS_UNREACHABLE`, and `NETWORK_CHANGED`. `net::ERR_TIMED_OUT` is excluded because the request may already have reached the server. This is not a strict never-sent rule: `EMPTY_RESPONSE` and the reset/closed/aborted failures can also occur after the server has received the request, so the retry deliberately accepts a possible duplicate top-level GET for those classes. Pages whose GET navigation has server-side effects should not rely on this automatic retry. Each `browsingContext.navigate` dispatch itself uses `allowAmbiguousRetry=False`. If the original command is rejected because the page started a concurrent navigation, the wrapper does not blindly resend the target URL; it adopts a successor navigation only when an owner-context `browsingContext.navigationStarted` event can prove that supersession.

With the default `requireHttpStatus=True`, the transaction binds the navigation ID returned by `browsingContext.navigate` and accepts only the correlated main-document response. The status source is chosen when the transaction starts. If GLOBAL `network.responseCompleted` is already active (for example because Discovery recording or a network signal subscribed it), no `responseStarted` subscription is added and the correlated response is captured from `responseCompleted`. Otherwise the transaction acquires `network.responseStarted` and holds it through settlement. A subscription the transaction created is released in its cleanup on a best-effort basis: the registry entry is removed only after `session.unsubscribe` is positively acknowledged and is otherwise retained so `ClearState` or `Shutdown` can retry. If a GLOBAL `network.responseStarted` subscription already exists, the transaction only borrows it and never removes it; ownership is checked by subscription ID before any unsubscribe is attempted.

Before the capture is armed, one ordinary `ProcessRecorderQueue` batch (up to 1,000 messages) dispatches already-buffered events so that only events after the arm boundary can satisfy the transaction. Separately, each `browsingContext.navigate` attempt runs a fairness-bounded `DrainNonBlockingRecorderQueue` immediately before arming the concurrent-navigation supersession watch. In v5.3, Discovery recording no longer pauses GLOBAL `network.responseCompleted` during the following URL/readyState stability and SPA-settlement phases. If Discovery is active, response observation remains continuous, and because GLOBAL `responseCompleted` is then already subscribed, a navigation started during recording does not add a temporary `responseStarted` subscription at all. This removes the former Recorder observation-gap/restore path without changing the public HTTP-status contract.

The public return value remains the real HTTP status string: HTTP 200 returns `"200"`, HTTP 404 returns `"404"`, and so on. Non-HTTP navigation, a missing navigation ID, or any state in which the correlated main-document HTTP status cannot be established fails with `HttpStatusUnavailable` rather than fabricating a synthetic `"500"`.

Unlike the file-dialog, new-context, and download captures, the HTTP-status capture does not treat event loss after its arm boundary as fatal once a status has been captured. The capture keeps the correlated response with the greatest `redirectCount` observed for the navigation ID. If a status is known when settlement ends, it is returned even if asynchronous event loss occurred after the arm; the loss count (total asynchronous loss, not a navigation-specific class) is consulted only to explain `HttpStatusUnavailable` when no status was captured. Consequently, if the event for the final hop of a redirect chain is lost, for example through FIFO eviction during a heavy navigation, the status of an earlier hop such as `"302"` may be returned. Zero event loss is not a final-hop guarantee either: after settlement the method performs a single `ProcessRecorderQueue` pass (at most 1,000 messages) and does not wait for the final response event to arrive or be dispatched, and settlement itself is best-effort. An earlier observed status can therefore also be returned when the final event is merely late. The communicator's loss counters and the session-drop summary explain one cause of a stale status, not its absence.

With `requireHttpStatus=False`, the same navigation and optional SPA settlement run without creating the HTTP-status capture, and the method returns an empty string. Navigation and protocol failures still raise. `ERR_CONSENSUS_HALT` continues to propagate, and the navigation-status transaction is protected by the Chapter 5 exclusive one-shot capture owner.

> **Compatibility note (change introduced in v4.1):** This public contract intentionally changed. Code written around the old synthetic **`"200"` / `"500"`** convention should now expect real HTTP 4xx/5xx status strings and exceptions when HTTP-status correlation itself cannot be established.

## History Traversal Without Replay

`ExecuteTraverseHistory` sends `browsingContext.traverseHistory` with an explicit nonzero `delta` and treats the command as state-changing. It disables ambiguous retry, recovery replay, and context retargeting because a timeout or context-loss response may occur after the browser already accepted the traversal. After a confirmed protocol response it runs the ordinary bounded post-action SPA synchronization when requested; an ordinary settle failure does not undo the accepted history change, while `ERR_CONSENSUS_HALT` still propagates.

## Chapter 17 — Logging and Traceability

## Two Log Products, Three Diagnostic Destinations

The project has two persistent diagnostic products when applicable, but three diagnostic destinations:

- `discovery_log.txt` is the browser-operation timeline. It records DOM, network, completion-signal, SPA-wait, invalid-filter, and signal-context observations used to analyze and tune synchronization behavior.
- `bidi_socket_trace.log` is the conditional communicator and transport incident record. Since v5.4, a direct `Connect` first deletes any previous trace file and ordinary startup does not recreate it. The file is recreated lazily only when a **critical diagnostic is actually written**. That trigger is broader than a socket/WebSocket error: it includes transport/recovery/heartbeat failures, oversized-message identity diagnostics, selected security/re-entry connection rejections, and a nonzero session-drop summary. Recovery reconnects do not perform the direct-connect deletion, so they keep the incident history.
- The **Immediate Window** is the transient diagnostic surface. It carries wrapper-side action, wait, and recovery messages under `BiDiCommandWrapper.DebugMode`, operator-facing detail such as the outstanding-URL list printed on a CONSENSUS HALT, and communicator chatter under `COMMUNICATOR_DEBUG_ENABLED` or `WINSOCK_TRANSPORT_DEBUG_ENABLED`. It is also the deliberate destination for a small number of ungated error handlers in **both** layers, where writing to a file would itself be unsafe. When a log file is written, `StopAndSaveDiscoveryLog` additionally prints the saved path and a one-line Stop timing summary to the Immediate Window regardless of `DebugMode`; this is residual profiling output and is not a third persistent log product.

The communicator's `Trace` routine is itself a non-raising diagnostic boundary: it enters `On Error Resume Next` before timestamp formatting, Immediate Window output, log-directory resolution, `FreeFile`, file open/write, and close work. A logging failure therefore cannot replace the transport error already being handled or break cleanup simply because a state transition or diagnostic path reaches `Trace`. Some cleanup-critical sites still use direct `Debug.Print` or store failure state for later emission; that is an output-placement choice rather than a requirement imposed by `Trace` throwing. Where the underlying transport cause is stored by `WsSetFailure`, safe outer detection sites can still reconstruct it through `GetWinsockFailureText()` for the persistent critical record.

This is an output-destination distinction, not a third log product. Wrapper recovery messages such as `BiDi [RECOVERY FAIL]` remain in the Immediate Window. What propagates to the caller is the original command error, not the recovery failure reason, and transport-caused recovery failures are already covered by the communicator’s critical pass-through. Protocol-layer recovery detail therefore stays transient unless a future unattended-operation requirement justifies a dedicated persistent wrapper error log — which would be a new product, not an extension of either existing one.

Keeping these three destinations distinct prevents low-level socket history and transient wrapper diagnostics from contaminating the browser-operation timeline used for wait tuning.

## AI-Ready Discovery Recorder — High-Purity Procedure Logs

BiDi messages are accumulated by the communicator and cooperatively drained into the recorder queue during VBA polling. This is passive with respect to the browser event stream; it is not a separate asynchronous VBA thread.

- **Dynamic noise filtering with accounting:** URL and MIME filters suppress static resources, script loads (`excludeScripts`, default True), telemetry, and other configured noise. The tail includes `[SUPPRESSED-TOTAL]` and per-key `[SUPPRESSED]` counts so filtering is visible. Since v5.2 the suppression key is intentionally coarse: normalized host+path plus query presence only, with query names and values omitted.
- **Normalized endpoint shape for AI:** timeline network keys remove fragments, preserve query parameter names while stripping values (except `rpcids` and identifier-shaped `action` values), and redact matrix/path assignment values. This preserves useful API shape without carrying volatile query values into the log.
- **Log safety:** network keys drop fragments and query values (except `rpcids` and identifier-shaped `action` values), and `[NAV]` lines redact the whole fragment as `#<fragment-redacted>`. BODY STORE, path segments (for example mailbox identifiers or object IDs), and the Immediate Window's CONSENSUS HALT URL list are not redacted; review a log before sharing it.
- **Optimized for direct LLM ingestion:** The file begins with a compact conceptual header and uses tagged timeline lines with relative timestamps such as `[1.23s]`. It is saved as UTF-8 without a BOM. Event, signal, and SPA-wait lines use a 5,000-entry ring-buffer helper, while the final suppression summary is appended directly and BODY STORE is written separately; therefore 5,000 is not a strict whole-file limit.
- **Two time axes:** the leading `[t]` on every timeline line is when the recorder or wrapper processed or observed the line, so the timeline is monotonic. Event-derived lines (`[REQ]`, `[RES]`, `[ERR]`, `[BLOCK]`, `[NAV]`, console lines, and a network `[SPA-SIGNAL-HIT]`) also carry `at=<sec>s`, the socket arrival time of the underlying BiDi event (`LastEventArrivalMs`). SPA diagnostics (`[SPA-ACT]`, `[SPA-WAIT-*]`, `[SPA-STABLE]`) have no arrival time and carry only `[t]`. The two agree within about 0.1 s when the queue is drained promptly, but `[t]` can lag `at=` by seconds when events queue faster than the recorder dispatches them: on Outlook on the web the lag reached about 13 s during application boot and several seconds during native key input, while arrival order and event completeness were preserved (no loss was recorded). Read ordering from `[t]` and event timing from `at=`. `at=` is emitted only while recording, so Immediate Window signal lines outside a recording carry no arrival stamp. Arrival stamps were not substituted into `[t]` because a backlog would then make later-dispatched lines carry earlier times. Internally the same separation holds: `m_sigNetHitMs` is the recognition time used for `observedMs`, while completion intervals use the arrival time.
- **Recorder health:** `[RECORDER-QUEUE-STATS]` at the end of the log shows whether the Recorder kept up (dispatch lag, FIFO depth, drain gaps, loss) and where its time went (parse versus fast path). A large `maxDispatchLagMs` or a `maxEventFifoDepth` approaching 2,000 means the recording itself may be shifting the timing of waits and element searches; compare against a run with recording off before tuning waits from that log. `fallbackOriginalParse` should be 0. `transportOversize=` inside `asyncLossSinceStart` identifies loss caused by oversized messages, such as an image request whose URL is a multi-megabyte `data:` URI; that loss is expected and is not a Recorder failure.
- **No temporary performance sidecar:** the `.perf.txt` instrumentation used while profiling Discovery shutdown has been removed. Normal Discovery recording now produces only the requested Discovery log and its in-file diagnostics; it does not emit the temporary performance sidecar.
- **Request lifecycle and observation coverage:** `[REQ]` and `[RES]` share the BiDi request ID, while redirects reuse that ID across hop-specific `redirectCount` values; `dur=` is not computed. In v5.3, Discovery keeps GLOBAL `network.responseCompleted` subscribed through navigation settlement, so the former Recorder pause/resume diagnostics are removed. `[REQ-UNPAIRED]` now classifies remaining unmatched hops as `open-at-end` or `other`.
- **Selective BODY STORE:** response-body capture is enabled by default, request-body capture is disabled by default, and eligible JSON payloads correlate to `[REQ]` / `[RES]` through the same ShortId + public normalized key while using a separate internal full-URL identity for BODY caps. Default retrieval/logging is top-context + same-origin/same-site/none; explicit patterns are the opt-in allow-list override. `[BODY-STATS]` summarizes normalization, compaction, truncation, misses, and skip categories before detailed inspection.
- **Transport-aware investigation:** `MaxIncomingSize` bounds oversized inbound messages before they can dominate VBA memory. A separate 512-byte identity prefix and full observed-byte counter produce one critical diagnostic at the message boundary, while v4.6 can fast-discard already rejected payload bytes in direct chunks of up to 256 KiB without crossing a WebSocket frame boundary. The event FIFO independently protects completed asynchronous traffic by count and bytes. At the recorder boundary, `TryGetParsedEvent` can reject a large or malformed completed event and continue to the following event without treating the drop as an empty queue.

## Log-Based Operator Tuning Rules

By analyzing `discovery_log.txt`, the operator feeds back into synchronization code:

- **Exclusion-filter judgment:** If ad, analytics, or beacon traffic remains pending, add a pattern with `AddIdleIgnoreNetworkPattern`.
- **Wait-time judgment:** After known noise is excluded, a `HALT` with legitimate pending URLs may justify increasing `maxTimeoutMs`, but only after ruling out stalled or ignorable traffic.
- **Outcome-based triage:** `HALT`, `TIMEOUT`, and `ERROR` have different meanings. Timeout tuning does not repair probe loss, socket failure, or a lost completion gate.
- **Recorder-coverage triage:** v5.3 keeps GLOBAL `network.responseCompleted` continuously subscribed while Discovery recording is active, so legacy `REC-PAUSE*` coverage markers should not appear in current logs. Use `[REQ-UNPAIRED] open-at-end|other` to classify unmatched request hops, and do not treat an unmatched hop as proof that a response was lost by the Recorder.
- **Settle-to-render suspicion:** `[SPA-CONSENSUS-SUSPECT]`, `[SPA-CONSENSUS-UNRESOLVED]`, and `[SPA-CARRYOVER-NOTE]` are advisory markers based on the network completion interval (Chapter 3). `firstJson=<key>@<sec>` uses the communicator's event-arrival time (`LastEventArrivalMs`) relative to recorder start when available; only if no arrival timestamp is available does it fall back to the current VBA monotonic time. SUSPECT means no content render at or after the response's lower bound although the response completed inside probe observation; treat that STABLE as possibly premature. UNRESOLVED means the render order cannot be determined (INDETERMINATE: render inside the interval; UNOBSERVED: the response may have completed before observation began) and must not be read as SUSPECT. The absence of these markers does **not** prove render safety, especially when the relevant response or network HIT happened before `[SPA-WAIT-BEGIN]`. BODY STORE presence or ordering proves capture, not response-to-render timing. `[SPA-NET-TO-CONTENT]` reports `relation`, `delayMs=min..max`, and `widthMs`; a `delayMs` upper end near or above `minStableMs` is a warning / uncertain zone rather than proof of premature completion, and the upper end may be conservative because only the latest change time per path is retained. `observedMs` is only the polling-observation delay. `owner=not-asserted` still means the timing does not prove causation. Prefer a stable content/visibility gate, or a more conservative per-action `minStableMs` when capture correctness matters.
- **Filter validity:** `[SPA-FILTER-INVALID]` means an ignore selector threw in `Element.closest`; the Probe quarantines it and continues monitoring, but the operator should correct the selector.
- **Context alignment:** `[SPA-SIGNAL-CTX-MISS]` means the network pattern matched in a non-owner or empty context. The remedy is context alignment, not a larger wait window.
- **Incomplete DOM activity:** `changeOverflow=` above 0 on `[SPA-WAIT-END]`, or `dropped=` on `[SPA-ACT]`, means the probe could not list every mutation of that wait. Do not derive an `ArmContentSignal` path from the absence of a path in such a wait; the verdict lines remain valid because dropped content renders were counted.
- **Context of a network line:** `ctx=(empty)` on `[RES]` marks a worker-side request that idle consensus cannot see; `ctx=other:` marks another tab or frame (for example a sign-in iframe). Lines without `ctx=` belong to the recorder context shown as `recorderCtx=` in CONFIG.
- **Worker-side completion:** when an application's decisive request comes from a Web Worker (empty context, `[BODY-SKIP] reason=context-unknown`, or `hint=allowContextless-if-worker`), Fetch/XHR consensus cannot see it. Gate the action with DOM/visibility evidence or `ArmNetworkSignal ..., allowContextless:=True`; do not rely on idle consensus or a longer timeout.
- **Timeline lag:** a large difference between `[t]` and `at=` means the recorder was behind the wire, not that events arrived late. Judge event timing from `at=`.
- **Body-level API interpretation:** use response BODY STORE when endpoint names and status codes are insufficient to explain application behavior. With no explicit body patterns, remember that cross-site, child-context, and unknown-scope JSON is intentionally excluded from saved BODY output. Use `AddBodyCapturePattern` as an explicit allow-list when that broader capture is intentional, and treat `[BODY-SKIP]` / `[BODY-MISS]` as capture outcomes rather than proof that the HTTP body was empty.
- **Download correlation triage:** `[DOWNLOAD-BATCH-WILL-BEGIN-IGNORED]` or `[DOWNLOAD-BATCH-END-IGNORED]` with an uncorrelatable/unknown-correlation reason means the event arrived but could not be admitted to the active batch. That is a correlation problem rather than a slow transfer; extending `timeoutMs` does not repair missing identity.
- **Visible-first choice:** `[LOCATE-PREFER-VISIBLE]` means the XPath also matches hidden elements and a later visible one was used. That is usually the intended element; if not, tighten the XPath or set `PreferVisibleMatch = False`.
- **Trusted-click misses:** `[TRUSTED-HITTEST] reason=zero-box` means the locator resolved only to a hidden element; `covered` names the front element, such as a banner or overlay to close first; `no-element` points to a viewport or layout problem. `outcome=synthetic-fallback` means the action still succeeded through `element.click()`.

## Three Independent Debug Controls

The similarly named debug controls have intentionally separate scopes:

- `BiDiCommandWrapper.DebugMode` controls wrapper-side action, wait, and recovery messages.
- `COMMUNICATOR_DEBUG_ENABLED` controls outer communicator chatter such as request/response summaries, state changes, and ordinary `Trace` output.
- `WINSOCK_TRANSPORT_DEBUG_ENABLED` controls only the lowest-level integrated WinSock `OPEN`/`FAILED` direct diagnostics.

The two communicator constants are `False` in the production configuration. Disabling them does not suppress calls explicitly classified as critical.

## Critical Pass-Through in Production

`Trace(..., isCritical:=True)` bypasses `COMMUNICATOR_DEBUG_ENABLED` and writes the persistent trace whenever that critical path is invoked. Since v5.4, the trace file is no longer created eagerly at ordinary startup; it is created lazily by the first critical diagnostic. No separate “incident logging active” flag exists. A critical write can be caused by a socket/WebSocket failure, but also by non-error loss evidence such as a nonzero session-drop summary or by selected rejected connection paths. Critical coverage includes:

- IPv6-to-IPv4 connection fallback details;
- send failures;
- receive-side transport failure or loss of the open state, distinguished between event polling and command-response waiting;
- application-heartbeat reply timeout;
- oversized-message identity diagnostics with total observed bytes for the message, the configured limit, retained byte count, an ASCII-safe prefix, and the adjacent-object marker count;
- recovery attempts and results; and
- the final session-drop summary, including asynchronous-event loss, late/unknown command-response loss, recorder-side oversized/malformed/filtered parsed-event drops, and the classified lifecycle, download, file-dialog, and unknown-critical loss totals.

The low-level `WsSetFailure` routine stores the WinSock/internal error code and description while performing socket teardown. It does not call `Trace` from its cleanup-critical path. The safe outer detection sites retrieve those stored details through `GetWinsockFailureText()` and emit the critical incident record.

## Critical-Diagnostic-Activated Socket Trace

Since v5.4, a direct `Connect` calls `DeleteSocketTraceLogIfExists` before establishing the new session, so any trace left by a previous direct session is removed first. Ordinary startup does not create a replacement file. `bidi_socket_trace.log` is recreated lazily only when a call to `Trace(..., isCritical:=True)` actually writes a critical diagnostic.

“Critical” is intentionally broader than “socket/WebSocket error.” In addition to transport, recovery, and heartbeat failures, the file may be created by oversized-message identity diagnostics, selected rejected connection paths, or `TraceSessionDropSummary` when any tracked drop/loss counter is nonzero — for example FIFO eviction, a late response, recorder-side oversize/malformed/filtered loss, or transport oversized-message evidence. A heavy SPA can therefore produce a trace even when the socket itself never failed.

Recovery reconnects do not perform the direct-`Connect` deletion, so diagnostic continuity is preserved across recovery attempts. The converse is also important for unattended operation: a later **direct** `Connect` deletes the previous incident trace before the new session starts, so external preservation/rotation is required if evidence must survive a subsequent fresh run.

## Chapter 18 — Session Lifecycle, Atomic Initialization, and Reuse

## Atomic `ConnectTo`

`ConnectTo` validates the WebSocket URL and rejects an already connected or connecting communicator before dropping active wrapper state. Before reset, it preserves any subscription IDs whose remote cleanup was not confirmed. After the transport connects, the wrapper derives the BiDi session identity, binds the communicator's current connection generation, and reconciles deferred subscription IDs **before** creating new subscriptions in that same session. It then installs the four mandatory subscriptions — `log.entryAdded`, `browsingContext.navigationStarted`, `browsingContext.contextCreated`, and `browsingContext.contextDestroyed` — and snapshots the lifecycle-relevant loss baseline. Shadow Unlocker registration remains best-effort unless `requireShadowUnlocker:=True` is requested. If later initialization fails after session-side state has already been created, the error path clears the generation binding and first attempts Shadow-hook containment/restoration and bounded subscription cleanup while the socket is still live, then force-closes and re-raises the original error.

After the mandatory subscription succeeds, the connection path performs one best-effort **residual native file-chooser interception sweep**. A previous VBA project may have terminated after enabling Chromium `Page.setInterceptFileChooserDialog`, leaving browser-side state behind that a fresh wrapper object cannot remember. The wrapper therefore walks the current browsing-context tree, obtains available `goog:cdp` sessions, and sends the disabled state once per distinct Chromium page session. Lack of `goog:cdp` support is treated as a non-Chromium implementation and does not fail `ConnectTo`; an unconfirmed Chromium cleanup is retained as pending tracked state for later release attempts.

The same connection path also performs a best-effort **residual download-behavior clear** through `browser.setDownloadBehavior(downloadBehavior=null)`. Unsupported implementations are accepted. If cleanup is indeterminate on an implementation that appears to support the command, the wrapper records the download-behavior state as unknown and blocks the download engine (`ExecuteDownloads`) until an explicit `SetDownloadFolder`, `SetDownloadDenied`, or `ClearDownloadBehavior` succeeds.

The Shadow DOM Unlocker is registered during the same connection sequence. Its default contract is best-effort: failure produces a warning and the BiDi connection remains usable. Passing `requireShadowUnlocker:=True` promotes registration to a required part of atomic initialization. v4.4’s generation/containment guard also prevents a new active preload from being stacked on top of an unresolved ambiguous old registration unless that uncertainty can first be covered by a newer inert generation.

## Logical Connectivity Contract

`IsConnected` requires agreement between both layers: the communicator state must be `StateConnected`, the native transport must be initialized, and the WebSocket must report open. VBA’s non-short-circuit `And` is avoided through sequential guards. Consequently, a stale native handle that still appears open while the logical state is `StateError` never authorizes another command.

`IsTransportOpen` exposes the native WebSocket state for diagnostics only. It may briefly be True while `IsConnected` is False; command availability and recovery decisions must use `IsConnected`.

## Session-Continuity Binding

`ConnectTo` records the communicator's `ConnectionGeneration` before the mandatory subscriptions are made. The communicator advances that value in `FinalizeConnectedState` on every successful OPEN, including recovery reconnects, before `StateChanged` is raised; at the Long ceiling it wraps to 1, so a live connection never reports 0. While that binding is nonzero, the wrapper treats the session as lost when the communicator has been released, the generation differs from the bound value (a silent reconnect), or the communicator state is not `StateConnected`. Every `ExecuteBiDiCommand` dispatch and every wait heartbeat asserts this condition and raises `ERR_SESSION_CONTINUITY_LOST` (`vbObjectError + 1030`) with the reason. A value of zero means no bound session and disables the guard; `ConnectTo` failure cleanup, `SetSocket`, and `Shutdown` set it to zero.

The boundary is between temporary unresponsiveness and connection loss. A command-correlation timeout (604) on the same connection keeps the session usable, because the socket and its subscriptions are unchanged. Loss of the transport, or its re-establishment by communicator recovery, stops the session. The wrapper implements no automatic recovery from that state, and the error message deliberately gives no recovery procedure.

`CheckAlive(timeoutMs)` is the explicit liveness check for long gaps before the next action, such as heavy VBA work or manual waits. It returns True only when the bound connection is still the one `ConnectTo` subscribed on and the peer answers `session.status` within the timeout (default 3,000 ms). It never raises. `IsConnected` alone is cached state and can remain True for a dead or suspended peer until the next socket I/O.

## Transactional Discovery Recorder Start

`StartDiscoveryLog` treats event subscription and recorder-state publication as one transaction. New collections, timestamps, and body-collector state are staged locally, and `m_isRecording` is published last. v5.3 requires the exact GLOBAL `network.responseCompleted` subscription to be available before commit. An already existing global subscription is reused; otherwise one is created through the wrapper-wide active-subscription registry, with no Recorder-specific ownership ID. A context-scoped subscription does not satisfy this requirement. Response-body collection is requested by default; request collection is staged only when explicitly enabled. A collector capability failure is recorded as body-capture unavailability without disabling the ordinary recorder, while a later recorder-start failure best-effort removes any collector created during staging before re-raising the original error. Subscription failure re-raises the original error without clearing a prior recorder, losing its logs, or leaving an enabled recorder with uninitialized collections.

## Communicator Replacement Contract

`SetSocket` accepts neither `Nothing` nor a communicator that may still own transport resources. Both the current and replacement communicator must be fully disconnected; connecting, connected, disconnecting, and error states are rejected. On successful replacement the wrapper clears session-boundary state and caches before adopting the new communicator.

`UseWinsockTransport` remains only as a compatibility shim. WinSock is the sole transport: setting it to `False` raises, and confirming `True` is permitted only while disconnected.

## Idempotent Shutdown

`Shutdown` and `Class_Terminate` share one non-raising teardown path guarded by `m_shutdownCompleted`, preventing duplicate cleanup and duplicate completion diagnostics after teardown has actually finished. Teardown first releases the session-continuity binding, because best-effort cleanup may legitimately run on a degraded session and may still use the communicator's recovery path. It is not safe to call from a callback that runs during an `AllowUiPump=True` command-correlation yield (Chapter 2): browser-side cleanup and transport teardown can be rejected while the command still owns correlation. The wrapper therefore sets `m_shutdownCompleted=True` only after `ForceClose` / `Disconnect` leaves the communicator outside `StateConnected` / `StateConnecting`. If teardown is rejected and the transport remains live, `Shutdown` returns with the completion flag still **False**, allowing a later explicit call or `Class_Terminate` to retry once the owning command or `StateChanged` callback has returned. Once teardown begins it is otherwise best-effort and ordered around browser/session-side state. v4.4 first abandons any stranded exclusive capture, releases/contains tracked AutoClicker preloads, and releases the Global Shadow DOM Unlocker by removing the known preload when possible, restoring current-realm `attachShadow` hooks, and leaving a higher-generation inert containment preload. It then clears wrapper-owned global download behavior and releases any active Chromium file-chooser interception. Active request/response body data collectors are also removed on a best-effort basis before subscription and transport teardown so retained network payloads are not intentionally left behind.

While the BiDi socket is still live, Shutdown makes one bounded `session.unsubscribe` attempt for all active and retired subscription IDs. If confirmation is lost, it copies those IDs and the current BiDi session identity into the deferred-cleanup registry so a later same-session `ConnectTo` must reconcile them first. Only after this ownership step does the default `Shutdown ForceClose:=True` clear cached CDP state and force-close the socket; `Shutdown ForceClose:=False` may first detach the cached CDP session and then disconnect gracefully.

After browser/session ownership has been released or copied into a deferred registry, session-boundary flags and volatile caches are reset. This ordering prevents callbacks from observing a live flag whose backing collection has already disappeared and prevents unresolved subscription IDs from being forgotten. The disconnected communicator is retained so the same wrapper object may later reconnect; the active session identity itself can then be dropped because deferred cleanup carries its own identity.

## Chapter 19 — Development Conventions — The Four Golden Rules

To preserve the anti-freeze architecture and AI-ready traceability, use these rules as implementation defaults, subject to the explicit infrastructure exceptions stated below:

1. **Use the base path for ordinary interactions:** Request/response JavaScript should go through `Me.CallScript`, which applies `WrapInSafetyShell`. Persistent probes, preload scripts, protocol-native BiDi input commands such as `input.performActions` / `input.setFiles`, narrowly scoped CDP infrastructure, and explicitly best-effort PostScript cleanup are documented exceptions rather than reasons to bypass the base path casually.
2. **Heartbeat integration (**`hb`**):** JavaScript loops or polling must yield asynchronously and call the closure-provided `hb()` at the loop head. A synchronous blocking loop is forbidden because neither the browser watchdog nor VBA can pre-empt it.
3. **Timeout delegation:** Public interaction methods should expose an appropriate timeout and pass it to the shared execution path; non-interaction utilities such as state/cache helpers are exempt.
4. **Make VBA responsiveness owner-aware:** Ordinary outer waits should use `WaitHeartbeat`, which sleeps through `socket_.IdleReceive`; `socket_.PumpMessages` and `socket_.YieldExecution` remain for waits that must not take the receive side. `IdleReceive` itself falls back to `YieldExecution` whenever it cannot safely own receiving. If UI responsiveness is required during command correlation, do not insert direct `DoEvents`; use the public `AllowUiPump` property so the communicator owns the guarded yield boundary. `SendAndReceive` keeps response-ID ownership and nested BiDi commands are rejected by the re-entry guards.
